# タスクタイムラインアプリ 設計-v1

**アプリ名：SacSak**
**タグライン：サクッと置くだけ、今日の段取り。**
**アーキテクチャ方針：サーバーレス・ローカル完結（SwiftData、幽霊アプリと同系統）**

⸻

## 📝 このドキュメントについて

「アプリケーション設計-v10」の章構成に準拠しつつ、本アプリはローカル完結（SwiftData）のため以下の章は**対象外**として省略している：

- LLM / 外部APIレイヤー
- インフラ / デプロイ / API設計
- 自前サービス間連携（エコシステム用）
- ログ・監査・コスト可視化（サーバーサイドが存在しないため）

Googleカレンダー等の外部カレンダー連携は**意図的に非対応**。本アプリの管轄は「繰り返し使うTaskを、その日のタイムラインに柔軟に配置する」ことに限定し、固定の一回性イベント管理はGoogleカレンダー側に委ねる。

⸻

## ✅ コンセプト

**「タスクの在庫（Task）」と「その配置（Placement）」を分離する。**

既存のカレンダー/タスクアプリは「タスク作成＝時間確定」が1セットになっており、毎回フルセットの入力を強いられる。本アプリは、タスクを一度登録しておけば、日々のタイムラインに再利用・柔軟配置できる「在庫→配置」の2層構造を核とする。

⸻

## ✅ リリースフェーズ別スコープ

**0. 判断基準**

「無料/有料」ではなく、**「コアループの検証に必要か」**を唯一の判断軸とする。有料機能が後回しになるのは無料だからではなく、それを"欲しくなる文脈"（使い込んだ実感・複数パターンを作った経験）がv0時点ではまだ存在しないため。文脈がない状態で課金構造を作っても機能しない（pre-PMF段階での作り込み過剰を避ける）。

**1. v0（MVP・最速リリース目標）**

コアループが実際に回るかどうかだけを検証する。ここが崩れたら以降は全部無駄になる。

- ✅ Task CRUD（名前・詳細メモ・所要時間のみ。色タグなし）
- ✅ タイムラインへのタップ配置（空きスロット判定、15分刻みスナップ、durationのクイック上書き含む）
- ❌ プリセット6色 → モノトーンで開始
- ❌ オンボーディング → "appear and end"精神で無し。初見でも直感的に触れるUIを優先
- ❌ 通知（開始15分前） → v1.1へ
- ❌ テンプレ機能 → v1.1〜v1.xへ
- ❌ 投げ銭IAP / 履歴ゲート型サブスク → v1.x後半〜v2へ

**2. v1.1〜v1.x（無料おまけ・コアループの体験を底上げ）**

v0を実際に使い始めて「これが地味に欲しい」と分かった部分から順次追加。

- プリセット6色
- 通知（開始15分前）
- 軽いオンボーディング
- テンプレ機能（保存数の上限は未設定のまま様子見）

**3. v2以降（有料機能・文脈が生まれてから設置）**

「積み上がった」「複数パターン欲しい」という文脈がv1.xで実際に生まれてから着手。

- 投げ銭IAP（非消耗型、実装コストほぼゼロなので早めでも可）
- 履歴ゲート型サブスク（無料は直近7〜30日、以降有料）
- テンプレ保存数の上限設定と課金ゲート

## ✅ UX設計

**1. UX思想**

行動ループ：
```
Task登録（在庫を作る）
→ タイムラインへ配置（Placement）
→ 完了（即時報酬）
→ 履歴として資産化
→ 翌日また配置（再行動）
```

**2. コア行動**

- Task登録（在庫を増やす）
- タイムラインへの配置（在庫を当てはめる）

この2つ以外は全て補助機能。

**3. 報酬設計**

- タスク完了時の軽量フィードバック（トースト・チェックアニメーション程度、演出過剰は禁止）
- 15分刻みでの所要時間調整など、操作そのものの摩擦を減らすことが最大の報酬設計

**4. 資産化設計**

- ローカル完結のため「データが消える不安」による引き止めは機能しない
- 資産化の対象は**生データではなく閲覧レイヤー**（履歴・統計・グラフ）→ マネタイズ設計を参照

⸻

## ✅ 画面数・画面構成

**1. 画面数の予算**

- コア画面：3画面
- サポート画面：3画面
- エントリー画面：1画面
- 合計：**7画面**（+ モーダル拡張3種）

**2. 画面カテゴリ分け**

| カテゴリ | 画面 | 備考 |
|---|---|---|
| エントリー系 | オンボーディング（1画面） | 初回のみ。Task/Placement分離の考え方を軽く説明 |
| コア体験系 | ホーム/タイムライン、タスク一覧、タスク編集（モーダル） | アプリの魂 |
| サポート系 | 履歴・統計、設定、投げ銭 | たまに触る |
| システム系 | なし | v1は共通エラーモーダルで吸収 |

**3. モーダル拡張（画面数バジェット外）**

- タスク編集モーダル（タスク一覧からの呼び出し、または新規作成）
- テンプレ適用モーダル（一覧表示 = 管理の場を兼ねる。タップで適用、スワイプ/長押しで削除・リネーム）
- テンプレ保存モーダル（ホームのタイムラインから「今日の配置を保存」）

## ✅ データ設計（SwiftDataモデル）

**1. 全体方針**

- 使用：SwiftData（ローカル完結、サーバー同期なし）
- Task（在庫）とPlacement（配置）を明確に分離する設計を貫く

**2. モデル一覧**

```
Task
- id: UUID
- name: String                 // タスク名
- memo: String?                // 詳細メモ
- durationMin: Int             // デフォルト所要時間（分）
- colorTag: ColorPreset        // プリセット6色から選択
- createdAt: Date
- deletedAt: Date?             // 論理削除

Placement
- id: UUID
- task: Task                   // FK（リレーション）
- date: Date                   // 配置日（日付のみ、時刻は別カラム）
- startTime: Date              // 開始時刻
- durationMin: Int             // 配置時点でのコピー値。編集で上書き可能
- createdAt: Date

Template
- id: UUID
- name: String
- createdAt: Date

TemplateItem
- id: UUID
- template: Template            // FK
- task: Task                    // FK
- startTime: Date               // テンプレ内での相対開始時刻
- durationMin: Int
```

**3. 設計上のポイント**

- `Placement.durationMin` は `Task.durationMin` を初期値としてコピーするが、独立して編集可能（「今日は特別30分で」に対応）
- `Task` は論理削除（`deletedAt`）。過去のPlacement/TemplateItemが参照切れを起こさないための配慮
- テンプレ適用時は `TemplateItem` の中身をその日の `Placement` としてコピー生成する（テンプレそのものを直接参照しない）

⸻

## ✅ タイムライン操作設計

**1. 表示形式**

- 1時間刻みのRow構成（縦スクロール）
- 日付ナビゲーションは**横スクロール（ページング）のみ**。カレンダーピッカー等の遠距離ジャンプ機能は持たない
- 前日/翌日のプレビュー：スワイプ前に隣接日のタスク色をちょい見せ

**2. 配置フロー（タップベース、ドラッグ&ドロップは不採用）**

1. 空きRow（例：12:00〜13:00）をタップ
2. その時間帯の**空きスロット**を提示（既存Placementと重複する区間は選択肢から除外）
3. Task一覧から選択
4. Task選択時、`Task.durationMin` がデフォルト表示される
   - そのまま確定 → タップ1つで配置完了
   - 変更したい場合 → 15/30/45/60分のクイック選択で上書き
5. 開始時刻は15分刻みでスナップ

**3. 表示ロジックの注意点**

- Placementの所要時間がRowの時間帯（1時間）をまたぐ場合、ブロックの高さは時間軸に比例して複数Rowにまたがって描画される（「1タップ範囲＝1Row」と「ブロックの見た目＝時間軸比例配置」は別レイヤーとして扱う）
- 同一Row内に複数Placementが存在できる前提で、空きスロット計算ロジックを実装する（「その日の全Placementを時系列ソート→空き区間を算出」）

**4. 編集/削除**

- 既存ブロックをタップ → 編集/削除モーダル

## ✅ 通知設計

- 各Placementの**開始15分前に1回**通知
- 「15分刻みで毎回通知」は不採用（ノイズが多すぎるため却下）

## ✅ テンプレ機能

- ホームのタイムライン画面から「テンプレ保存」「テンプレ適用」を呼び出す
- 独立画面は持たず、モーダルとして実装（画面数バジェットに影響させない）
- テンプレ適用モーダルを開いた時点でテンプレ一覧が表示され、これがそのまま管理UIを兼ねる
  - タップ = 適用（`TemplateItem` → その日の `Placement` としてコピー生成）
  - スワイプ/長押し = リネーム・削除

⸻

## ✅ マネタイズ設計

**1. 基本方針**

コア体験（Task登録・タイムラインへの配置）は**完全無料・無制限**。理由：
- タスク登録数に低い上限（5〜10個）を設けると、オンボーディング中に価値を実感する前に壁にぶつかり離脱率が上がる
- 「柔軟に組み合わせたい」という当初の動機を無料版で完全に満たすことが、結果的に有料転換の土台になる

**2. マネタイズ導線**

| 種別 | 内容 | 実装形態 |
|---|---|---|
| 投げ銭IAP | 「開発者を応援」等、設定画面に非消耗型課金を1個 | `Transaction.currentEntitlements` のみ。レシート検証・リストア考慮ほぼ不要 |
| 履歴ゲート型サブスク | 無料は直近7〜30日分の履歴閲覧のみ、有料で全期間の履歴・統計・グラフ・ストリーク表示 | StoreKit 2 サブスク |
| テンプレ数上限 | 無料は1〜2個まで保存可、それ以上は有料 | ローカルでカウントチェックのみ |

**3. 解約時の挙動**

- サブスク解約後も**生データは一切削除しない**。有料範囲（全期間閲覧・グラフ等）が見えなくなるだけ
- 再課金で即座に全履歴が復活する体験を保証する
- ローカル完結アプリのため「データが消える」という脅しは機能しない。握れるのは生データではなく閲覧レイヤーのみ、という前提を徹底する

**4. v1では見送るもの**

- タスク登録数の制限（コア体験を妨げるため不採用）
- サブスクの複雑なプラン分岐（年額/月額切替、猶予期間等）→ pre-PMF段階でここに実装コストを割くのは時期尚早

⸻

## ✅ 不採用・保留にした機能（記録として残す）

| 機能 | 理由 | 扱い |
|---|---|---|
| ドラッグ&ドロップ配置 | 座標計算・スナップ処理・実機依存が重く、実装コストの割にv1では過剰 | v1.1以降で検討 |
| カレンダーピッカーでの遠距離ジャンプ | 横スクロールのみで十分と判断 | 不採用（明示的に切り離し） |
| Googleカレンダー連携 | OAuth・トークン管理・バックグラウンド同期が必要になり、ローカル完結の設計思想と矛盾する | 対象外（明示的に切り離し） |
| ウィジェット | 実装コストが乗るため | v2以降に持ち越し |
| 15分刻みの逐次通知 | ノイズが多すぎて使われなくなる | 不採用 |
