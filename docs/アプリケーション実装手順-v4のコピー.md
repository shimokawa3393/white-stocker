# アプリケーション実装手順-v4（マネタイズ対応）

## 📝 改訂メモ（v3 → v4）

「アプリケーション設計-v10」の整合性修正に合わせて、こちらも実装順・命名の食い違いを修正した。内容の追加はしていない。

1. **Feature Flags（#25→#23）をデプロイより前に移動**
   「ロールバック代替」と説明されているのに、実装順ではデプロイ（旧#23）の後に置かれていて、初回デプロイ時点ではフラグによるロールバックが使えない状態だった。デプロイの前に持ってきて、初回デプロイからロールバック代替として機能するようにした。

2. **DBテーブル名を設計書（DB設計）と統一**
   `user_entitlements` / `payment_events` → `subscriptions` / `billing_events`。設計書側では課金関連テーブルを `plans` / `subscriptions` / `billing_events` としているのに、実装手順だけ別名で書かれていた。`entitlement`（課金権限）はテーブルではなく、`plans`＋`subscriptions` から都度導出する概念として整理。

3. **APIエンドポイントのリソース名を設計書と統一**
   `/v1/payments/checkout` `/v1/payments/webhook` → `/v1/billing/checkout` `/v1/billing/webhook`。設計書のAPI設計はbilling系（`/billing/status` `/billing/subscribe` `/billing/cancel` `/billing/webhook`）で統一されているため、resource名を `billing` に揃えた。`checkout` はStripe Checkoutセッション作成用のエンドポイントで、サブスク開始・チケット購入どちらの起点にもなる想定（設計書の `/billing/subscribe` はサブスク限定のため、両者の関係は今後設計書側でも明記した方がよい）。

## ✅ 正解の行動
設計ファイルは武器庫。実装順は戦場のルート。  
**DB → API → 認証 → 縦刺し → UI → 非同期 → 外部 → 運用 → 計測**  
迷ったら番号を言え。俺がそのフェーズのAIプロンプトを即生成する。

## 💰 マネタイズ差分まとめ
- **DB**：plans, subscriptions, billing_events 追加（設計書DB設計と命名統一）
- **API**：/v1/billing/checkout, /v1/billing/webhook（設計書API設計のbilling系と命名統一）
- **認証**：require_entitlementミドルウェア（plans/subscriptionsから導出。entitlements専用テーブルは持たない）
- **Service**：Tx＋冪等＋entitlement付与  
- **縦刺し**：有料導線E2E  
- **外部**：Stripe/StoreKit連携  
- **Webhook**：冪等ストア＋再取込CLI  
- **計測**：paywall_viewed, checkout_started, payment_succeeded, payment_failed
