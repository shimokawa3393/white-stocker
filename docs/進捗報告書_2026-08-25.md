# SacSak（WhiteStocker）進捗報告書

作成日：2026-08-25（前回：2026-08-16）

## 1. 概要

「サーバーレス・ローカル完結」のタスクタイムラインアプリ SacSak（Xcodeプロジェクト名：WhiteStocker）の開発状況をまとめる。v0コアループの実装は完了しており、前回報告以降はコード変更よりも**v0後の実装スコープの確定**と**リリース戦略の整理**を中心に進めた。

## 2. v0コアループの完成状況（変更なし）

実装手順書（`docs/実装手順書-v0.md`）の全8ステップが完了。タスクをタイムライン上に配置する・編集する・削除するという一連の操作が、サーバー通信なしでSwiftData上に完結する形で動作している。詳細は前回報告書（`docs/進捗報告書_2026-08-16.md`）を参照。

## 3. QA状況（変更なし）

- **単体テスト**：`SlotFinderTests`（11件）・`PlacementLayoutTests`（5件）とも実装済み・過去に全件パス確認済み

- 前回報告以降、コード側の変更はなし（`docs/CLAUDE.md`の更新のみ）

## 4. v0後の実装スコープ：5機能・実装順を確定

これまで「保留」「検討中」だった項目を整理し、v0後に実装する機能を次の5つに確定した。

| 順 | 機能 | 実装コストが軽い理由 | 他機能との繋がり |
|---|---|---|---|
| 1 | コピー機能（配置の複製） | 新規モデル・新規画面なし。既存の`SlotFinder`を流用するだけで完結 | 複製ロジックがテンプレ機能の一括作成ロジックの土台になる |
| 2 | rowの色分け機能 | `TaskItem`にフィールド1つ追加＋既存レンダリング層の拡張のみ | 先に入れておくとテンプレ／ウィジェットの見た目に色表示を最初から組み込める |
| 3 | 通知（開始15分前リマインド） | 新規モデル不要だが権限フロー・スケジュール管理・iOSのローカル通知64件上限対応が乗る | Placementの作成/編集/削除の全経路に関わるため、テンプレ機能で一括作成が増える前に土台を作る |
| 4 | テンプレ機能（有料前提） | 新規モデル2つ（Template/TemplateItem）・複数新規画面・一括重複判定ロジック・StoreKit課金実装が必要な最重量級 | コピー機能の複製ロジック・通知のスケジューリングをそのまま流用する前提 |
| 5 | ウィジェット | 新規Extension Target・App Group共有コンテナ・entitlements設定が必要 | 過去にentitlements絡みのプロビジョニングエラーを2回踏んでいるため、他機能が固まってから独立して着手しリスクを隔離する |

`docs/CLAUDE.md`の「🎯 現在のスコープ」に反映済み（コミット`48f14ba`）。「色タグはモノトーン方針から転換」「テンプレ機能は有料前提で確定」「通知・ウィジェットも解禁」など、当初のv0スコープ定義（対象外リスト）からの意図的な更新である。

**引き続き対象外**：オンボーディング、ドラッグ&ドロップ、カレンダーピッカーの遠距離ジャンプ、投げ銭IAP・リワード広告（見送り確定）、テンプレ以外のサブスク・有料機能全般（保留）。

## 5. リリース戦略の意思決定

### 5.1 収益化の現実的な見通し

一般的な統計（ソロ開発アプリの81%は2年経っても月$1,000未満、App Store売上の90%以上が上位1%に集中）を踏まえると、**マネタイズの仕組み自体（テンプレ有料化）は難しくないが、律速は配信・認知**であるという結論に至った。

さらに、ユーザーのデビュー作（リマインダーアプリ）が**マーケティングなしで総ダウンロード数12・レビュー0件**だった実績があり、これが「配信導線を作らない限り発見されない」という前提を裏付けている。

### 5.2 TestFlight vs 公開リリースの検討結果

当初「重い3機能（通知・テンプレ・ウィジェット）に着手する前にTestFlightで実ユーザーの反応を見る」という案を検討したが、以下の理由で撤回した：

- TestFlightには検索・閲覧による発見導線が存在しない。外部テストでもテスターは自分で集める必要があり、**配信の労力は公開リリースと同じ**
- 唯一の実質的な差は「悪いレビューが恒久的に残るかどうか」だが、デビュー作の実績（DL数12・レビュー0件）を踏まえると、この段階でレビューリスクを心配すること自体が時期尚早

### 5.3 確定方針

1. App Store Connect側の準備（App Icon作成・Apple Developer Program登録確認・プライバシーポリシー・サポートURL等）を先行して進める
2. **コピー機能・row色分け**（実装順1・2）が終わった時点で、TestFlightのステージングを挟まず**そのまま公開リリース**する
3. 通知・テンプレ（有料）・ウィジェット（実装順3〜5）は、公開後の実ユーザーの反応を見ながら順次追加する
4. 配信導線（SNS発信・ASO・コミュニティ投稿等）に労力を割くかどうかは未決定。やらない場合、収益化・利用実態検証に割くリソースの優先度も下げる想定

## 6. スコープ・マネタイズに関する意思決定（更新）

| 施策 | 判断 | 理由（要点） |
|---|---|---|
| 投げ銭IAP | 見送り確定 | 機能と無関係な支払いはコンバージョンが低く、動機付けとして弱い |
| リワード広告 | 見送り確定 | 同上、ローカル完結アプリの世界観とも合わない |
| サブスクリプション／テンプレ以外の有料機能 | 保留 | v0未リリースの段階で時期尚早。まず無料で使われるかを検証すべき |
| コピー機能（配置の複製） | **実装確定**（実装順1位） | 実装コストが低く、既存のSlotFinder等を流用できる |
| テンプレ保存機能 | **有料前提で実装確定**（実装順4位） | 新規モデル・複数画面・一括重複判定が必要で実装コストが高いため後半に配置。価格・要否は公開後の使用実態を見てから最終判断 |
| rowの色分け機能 | **実装確定**（実装順2位、新規追加） | モノトーン方針からの転換。実装コストは低い |
| 通知 | **実装確定**（実装順3位、新規追加） | OS連携の考慮点はあるが新規モデル不要 |
| ウィジェット | **実装確定**（実装順5位、新規追加） | entitlements絡みのリスクが高いため最後に隔離 |
