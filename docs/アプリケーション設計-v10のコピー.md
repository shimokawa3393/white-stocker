## ✅ UX設計（改訂版）

**0. このセクションの役割**

実装チーム・デザイナー・将来の自分が迷わないよう、UX設計の章では最低限以下を明文化する。
- コア行動は何か（1〜2個）
- 行動ループ図（Trigger → Action → Reward → Asset → Return）
- 各画面がループのどこに位置するか
- 通知の種類と目的
- 資産として残るもの一覧
- 追うべきKPIと、想定する数値レンジ（ざっくりでよい）

⸻

**1. UX思想**

人は **"即時報酬" に惹かれ、"蓄積資産" に縛られる。**
本アプリのUXは、

手段（アプリ利用）
→ 必要性（やる理由）
→ 行動
→ 報酬（短期快感）
→ 資産化（積み上がりの実感）
→ 再行動

このループを途切れさせないことを中核とする。

⸻

**2. UXゴール**

- **ユーザー側KGI**
  - 「このアプリを使うと、自分の〇〇（スキル／記録／人間関係など）が確実に前進している」と実感できる状態
- **プロダクト側KGI**
  - 30日継続率 / コア行動（例：投稿・学習・記録など）の平均回数が、ターゲットセグメントで目標値を超えている状態
- **代表KPI**
  - Day1 / Day7 / Day30 継続率
  - 1セッションあたりコア行動数
  - 新規ユーザーのオンボーディング完了率
  - 通知タップ率（起動トリガーの有効性）

⸻

**3. 行動ループ設計（Universal UX Loop）**

ユーザーの1サイクルを以下で定義し、すべての画面・機能はこのどこに属するかを明示する。

1. **Trigger（起動理由）**
   - プッシュ通知 / メール / ウィジェット / 他ユーザーからの反応 / AIからの提案
2. **Action（コア行動）**
   - 本アプリで最も価値のある行動（例：投稿・学習・記録・作成など）を1〜2種類に絞り込む
3. **Reward（即時報酬）**
   - フィードバック（スコア・コメント・演出・メッセージなど）を **1秒以内に返す**
4. **Asset（資産化）**
   - 行動が履歴・グラフ・マップ・コレクションなどとして残り、後から振り返れる状態
5. **Return（再起動の種）**
   - 「続きが気になる」「反応が来る」「進捗が伸びる」と感じる要素を用意し、次回起動の理由にする

⸻

**4. 報酬設計（短期UX）**

- **目的**
  - 操作ごとに「やってよかった」と感じさせ、次のアクションに自然に繋げる
- **感情ターゲット**
  - 小さな達成感
  - 自分への納得感
  - 他者・システムからの承認
- **具体手段**
  - 入力直後の軽量アニメーション・トースト
  - スコア・評価・進捗インジケータ
  - AIコメント・フィードバック（短く、刺さる一言）
  - ローディング中は必ず状態を示す（スケルトンUI／簡易スピナー＋テキスト）
- **KPI**
  - コア行動から離脱までのステップ数
  - コア行動完了率（開始 → 完了）
  - 1セッション内のコア行動回数
- **アンチパターン**
  - 演出過剰（毎回ド派手なアニメーションで飽きさせる）
  - 長文ポップアップ乱発で流れを止める
  - 報酬が抽象的すぎて「何が良かったのか」が分からない

⸻

**5. 資産化設計（長期UX）**

- **目的**
  - 「今までの努力・行動・作品がここに詰まっている」とユーザー自身が感じる状態を作る
- **資産の種類**
  - 行動ログ（例：投稿・記録・セッション履歴）
  - 実績・マイルストーン（バッジではなく"意味のある区切り"）
  - ナレッジ・作品・日記・コレクション
  - 他者との関係性（フォロー・返信履歴など）
- **可視化方法**
  - タイムライン（時系列）
  - カレンダー・ヒートマップ（頻度）
  - グラフ（成長曲線）
  - 一覧（作品・投稿ギャラリー）
- **KPI**
  - マイページ閲覧率
  - 過去ログに戻る行動の頻度
  - 「今月の自分の変化」に関わる画面の滞在時間

⸻

**6. 画面タイプと役割**

画面は「役割」で分類し、1画面1目的を徹底する。

1. **Hub画面（ホーム・ダッシュボード）**
   - 今日やるべきこと／続き／最新の反応を一覧で見せる
   - 「次にやる1アクション」を常に明示する
2. **Detail画面（閲覧・個別コンテンツ）**
   - 情報の理解と共感に集中させる
   - ここから起こさせたい行動は1〜2個に絞る
3. **Creation画面（入力・投稿・作成）**
   - フォームは極力シンプルに
   - 必須入力は最小限、補助情報は折りたたみ
4. **Myページ／資産画面**
   - 自分の積み上げが一目で分かる
   - "振り返り" と "次の一手" を同時に提案する
5. **設定・ヘルプ画面**
   - 操作ノイズにならないよう、深い階層に隔離
   - クリティカルでない限り、ユーザーフローの主役にしない

⸻

**7. 通知・リマインド設計**

- **目的**
  - 「アプリを再び開く理由」を提供する（ストリーク維持ではなく、本質的な必要性）
- **通知の種類**
  - 進捗・残タスク通知：「今週の目標まであと◯◯」
  - 他者反応通知：「あなたの◯◯に新しいリアクション」
  - 提案型通知：AIやシステムからの「こうしてみない？」の一言
  - 振り返り通知：「◯ヶ月前のあなたの記録」
- **ルール**
  - 1日あたりの通知上限を設計段階で明示
  - スパムと取られるパターン（意味のない連打）は禁止
  - 通知タップ後は、必ず「価値のある画面」に直接遷移させる

⸻

**8. 離脱ポイントとガード設計**

典型的な離脱ポイントをあらかじめ定義し、UXで潰す。

- **初回登録直後**
  - 対策：チュートリアルを極小化し、すぐに"1回やってみる体験"へ誘導
- **初回投稿・初回学習前**
  - 対策：テンプレ／サンプル／ワンタップ例文などで「失敗しようがない」状態を作る
- **数日ログインなし**
  - 対策：通知で「途中の状態」や「未完了タスク」を見せて、自然な復帰理由を作る


⸻

## ✅ マネタイズ設計（改訂案 v10）

**0. このセクションの役割**

マネタイズは「お金を取る仕組み」ではなく
**"継続させる体験の延長線"** にあると定義する。
無料→有料の移動を
- 不便の押し売り
- 強制的な閉塞感
- アプリ疲れ
に頼らず、
**"気づいたら課金しているUX"** を目指す。

⸻

**1. マネタイズ方針（全体の思想）**

**1-1. 課金は「便利の延長」**

- 無料ユーザーは **コア体験ループの80%** を味わえるようにする。
- 残りの20%（深み・快適性・拡張性）が「有料」。

❌ 無料ユーザーを締め付ける
⭕ 無料のままだと "惜しくなる" バランスにする

**1-2. 単発課金とサブスクの「役割分担」**

- **サブスク：毎日触るやつを強化**
- **チケット：集中したい瞬間をブースト**
- **買い切り：世界観の装飾（DLC・テーマ・キャラ）**

この3層で構成し、絶対に混ぜない。

⸻

**2. プラン構造（例）**

プロダクトに応じて数字は調整するが、構造は共通。

**2-1. 無料プラン**

- コア体験ループ（1日○回までフル解放）
- 基本的な保存・履歴閲覧（直近○件）
- 広告は入れない（集中の邪魔になるサービスではNG）
- AI生成系は
  - **1日3回**／**月20回** など "物足りるけどちょい足りない" 数に調整

**2-2. サブスク（メイン課金）**

- 月額：680〜1,200円帯（一般ユーザー向け）
- 以下を解放：
  1. 生成回数の大幅増
  2. 長文生成／高精度モデル使用
  3. 全履歴の保存・検索
  4. 月次レポート
  5. PDF / エクスポート
  6. テーマ変更・キャラクター強化

ポイント：
サブスクは「毎日見る画面」が明確に変わるようにする。
例えば "サブスクユーザー専用のホームWidget" を持たせる。

**2-3. チケット制（Pay-As-You-Go）**

- 100〜300円の軽い課金。
- 課金理由は「特別な1回」に寄せる。

例：
- こえあつめ：
  →「今日の声を最高画質で物語化」
- LimeStudent：
  →「英作文をプロ講師クラスで添削」
- TripCraft：
  →「旅程を"豪華ルート"で生成」

ポイント：
**「チケットを使うのは嬉しい」** という心理を設計する。
"回復アイテム" のように「ここぞ」で使われるUXにする。

⸻

**3. 課金導線（Paywall UX）**

**3-1. 課金訴求のタイミング**

**成功体験直後にしか出してはいけない。**

避けるべきタイミング：
- 作業前
- 空の状態
- ログイン直後
- アラートとして出す

出すべきタイミング：
- 生成が「驚くほど良かった瞬間」
- 履歴を眺めてニヤけた瞬間
- 月次レポートを見た後

⸻

**3-2. 課金画面の構造**

課金画面は以下4要素だけ：
1. **Before / After** の比較（視覚的に）
2. 月額・年額・チケットの3択（パッと選べる）
3. 解約が簡単である表示（信頼性）
4. 「あなたのデータは消えません」保証

※文字を減らし、画像または図で表現する。

⸻

**4. 継続率を支える仕組み**

**4-1. 継続させる価値**

- 週次ハイライト
- 月次サマリー
- 年間アーカイブ（育ち/成長/資産）

これらは有料限定にすると「継続理由」になる。

**4-2. 「無料ユーザーでも毎日起動する」UI**

- ホームに必ず「今日の一手」
- 一手を終えたら "次にやるべきこと" を自動提示
- "途切れない習慣" の演出：
  - 連続日数
  - 月のペース
  - 小さな進歩の可視化

⸻

**5. 休眠復帰 × マネタイズ**

休眠復帰の瞬間こそ「課金しやすい瞬間」。

- 1週間の休眠
  →「今日の1回だけサブスク機能が無料に」
- 1ヶ月の休眠
  →「復帰ギフトとしてチケット1枚」
- 生成後のフィードバック
  →「これ気に入った？残すならサブスクにしておけ」

⸻

**6. No Mercy ルール（マネタイズ編）**

- 課金しないユーザーに **ストレスを与える課金導線は禁止**
- コア体験を **奪う** のではなく、コア体験を **"伸ばす"** のが課金
- 課金要素は **3つまで**（多いと逃げる）
- 「便利さ」を先に体験させ、後でロックする
  → 逆は絶対にダメ
- 課金によって
  **"ホーム画面が変わる"** 体験を必ず用意する
- 新たな課金要素を追加する時は
  **既存の何かを削る**  

⸻

## ✅ 主要技術選定（改訂案 v10）

**0. このセクションの役割**

この章のゴールは
**「このプロダクトは、なぜこの技術スタックで作るのか？」**
を 1 ページで説明できること。
- 「好きだから」「慣れてるから」は理由にならない。
- 採用理由：**UX要件／開発スピード／運用コスト**
- 不採用理由：**学習コスト／オーバースペック／継続性の低さ**

⸻

**1. アーキテクチャの型を先に固定する**

まず「何をどう組み合わせるのか」の型を決める。
- Web系なら、どれに当てはめるかを1行で決める：
  - A. **SPA + API**（例：Next.js SPA + Django REST）
  - B. **SSR / SSG**（例：Next.js App Router + API Routes + 少量のBFF）
  - C. **純バックエンド + ネイティブアプリ**（例：Django API + SwiftUI）
- 型が決まらないまま技術名だけ並べるのは禁止。

ここに書く：
- 採用アーキ型：例）B. SSR / SSG + ライトAPI
- 理由：
  - SEO / 共有しやすさが重要か
  - インタラクションの複雑さ
  - 個人開発での実装コスト

⸻

**2. クライアント層（フロントエンド）**

**2-1. Webクライアント**

- **フレームワーク**
  - 原則：TypeScript + React or Next.js を標準とする
  - MicroFW（お前の Gustly-V 系）を使う場合は、
    「どこまで / なぜ自作を使うか」を明文化する。
- **選定軸**
  - UIの複雑さ（フォーム多い？グラフ？アニメーション？）
  - 将来の拡張性（他ページ・他機能を追加しやすいか）
  - LLMとの対話UIを前提にするかどうか

書くべき内容：
- 採用技術：Next.js (App Router) + TypeScript + CSS Modules or Tailwind
- 不採用技術：Vue / Svelte / jQuery など（※理由を書く）
- 理由：
  - 「既に Next×TS スタックの資産がある」
  - 「LLM連携のUIコンポーネントを流用できる」など

**2-2. モバイルクライアント（必要な場合）**

- iOS: Swift + SwiftUI
- Android: Kotlin + Jetpack Compose or クロスプラットフォーム

書く：
- ネイティブを選ぶ／選ばない理由
- WebView ハイブリッドは封印か許可か

⸻

**3. サーバーサイド / API 層**

**3-1. メインフレームワーク**

- Python系を軸にするなら：
  - **Django + DRF**
    - 採用条件：
      - 認証・管理画面・REST API・管理ツールを一気に仕上げたい
      - DB しっかり使うアプリ（LimeStudent, こえあつめ みたいな）
  - **Flask / FastAPI**
    - 採用条件：
      - とにかく小さいAPI
      - バックエンドの責務が薄い or 将来捨ててもいい PoC
- Node系を使うなら：
  - Next.js API Routes or NestJS を使うかどうか

書く：
- 採用：Django + Django REST Framework
- 非採用候補：FastAPI, NestJS など
- 理由：
  - 認証や管理画面を早く作りたい
  - 既存プロジェクトとの共通化（Docker・CI・監視）

**3-2. 認証・権限**

- 認証方式：
  - SPAなら：JWT + Refresh Token
  - SSR/Webなら：Cookie セッション + CSRF 保護
- 権限：
  - 「ユーザ / 管理者 / スーパーユーザ」程度に割り切る

⸻

**4. データベース / ストレージ / キャッシュ**

**4-1. データベース**

- 原則：PostgreSQL を標準とする。
- 理由：型しっかり・JSONB・拡張性・Render 等との相性
- 例外（MySQL, SQLite）は理由があるときだけ。

書く：
- 採用DB：PostgreSQL
- モデル設計の思想：
  - 正規化どこまで
  - ログ系は別テーブル／別DBに分けるか

**4-2. ストレージ**

- バイナリ：
  - 画像・音声 → S3互換 (Cloudflare R2 等)
- その理由：
  - 将来のCDN配信
  - スマホアプリ・Webから共通利用

**4-3. キャッシュ**

- セッション・頻出クエリ・LLMレスポンスのキャッシュ → Redis
- どのレイヤーでキャッシュするか：
  - APIレスポンス
  - LLMの回答
  - 集計済みの統計

⸻

**5. LLM / 外部API レイヤー**

**5-1. LLM プロバイダ**

- ベース：OpenAI（gpt-5.1, 5.1-mini など）
- 使い分けの大方針：
  - 通常：5.1-mini
  - 重いタスク / 重要出力：5.1
- ⚠️ **コンテンツ種別ごとの詳細なモデル割当・トークン上限は、ここではなく「コンテンツ生成・配信パイプライン設計 3-2」を正とする。** ここは大方針のみ。両方に数字を書くと改定時に食い違うので、詳細側だけ更新すること。

**5-2. アクセス方式**

- サーバーサイド経由でのみ呼ぶ
  → クライアントから直呼びは禁止（キー漏洩防止）
- 呼び出し用の専用モジュールを1つ用意：
  - llm_client.py みたいなやつで、
    - リトライ
    - ログ
    - モデル切替
  を一括管理。

**5-3. 他の外部サービス**

- 課金：Stripe
- ログイン：Apple, Google OAuth (必要なら)
- メール：SendGrid / Amazon SES

ここに「採用サービス」と「代替候補」「切り替え方針」を書く。

⸻

**6. インフラ / デプロイ / 開発フロー**

**6-1. インフラ**

- ホスティング：
  - Backend：Render / Fly.io / 自前 VPS のどれかに固定
  - Frontend：Vercel / Cloudflare Pages など

書く：
- 本番：Render + PostgreSQL + Cloudflare R2 + Cloudflare CDN
- ステージング：同構成 or SQLite + ローカルDocker

**6-2. コンテナ / Docker**

- Docker は「標準構成」を 1 パターン決めておく：
  - web（app）/ db / cache / worker 程度
- プロジェクトごとに構成をバラさない。

**6-3. 開発フロー**

- GitHub を前提：
  - main / dev / feature ブランチ方針
- CI（最低限）：
  - lint
  - type-check
  - unit test（一部だけでも）

⸻

**7. 技術選定ルール（No Mercy）**

- **新しい技術を入れるときのチェック項目：**
  1. その機能は 既存スタックで **「やろうと思えば」実現可能か？**
     → Yes なら「入れたいだけ」。却下候補。
  2. 6ヶ月後もまだメンテする気があるか？
  3. 他プロジェクトでも再利用するか？
- 禁止ルール：
  - 複数のフロントFWを1プロジェクトに混在させる
  - DBを用途もなく2種類以上使う
  - 小さい機能にサーバレス乱用して構成を複雑化する
- 許可ルール：
  - 「既存スタックでやると明らかに辛い領域」にのみ新技術を導入する。
    例）リアルタイム通信だけ Supabase / Firebase をスポット採用 など  
  

⸻

## ✅ 画面数・画面構成（改訂案 v10）

**0. このセクションの役割**

この章のゴールは **「このアプリは何画面で成立していて、どれがコアか」を一枚で伝えること。**
単なる画面一覧ではなく、
- 画面数の上限
- コア画面とオマケ画面
- 画面同士の役割分担
をはっきりさせる。

⸻

**1. 画面数の"予算"を先に決める**

まず、スマホ前提で 画面数の上限を決める。

- 原則：
  - コアアプリ：**8〜12画面以内**
  - 13画面を超える場合は、
    → 「本当に必要か？ 別機能として切り出すべきでは？」を再検討する。

ここに書く：
- 想定画面数（上限）：例）最大 10 画面
- コア画面：3〜5画面
- サブ画面：それ以外

⸻

**2. 画面カテゴリ分け**

全画面を、以下4カテゴリに必ず分類する。

1. **エントリー系**（入口）
   - スプラッシュ / 初回ガイド / ログイン・サインアップ
2. **コア体験系**（毎日使う）
   - ホーム / 入力画面 / 結果画面 / 履歴一覧 など
3. **サポート系**（たまに触る）
   - 設定 / プロフィール / 課金 / ヘルプ / お知らせ
4. **システム系**（裏方）
   - エラー画面 / 404 / 通信失敗リトライ / メンテ告知 等

ここで、「どのカテゴリが何画面まで許されるか」も決める：
- エントリー系：最大 2〜3 画面
- コア体験系：**アプリの魂。最優先。**
- サポート系：最大 3〜4 画面
- システム系：必要最低限、できるだけ共通化

⸻

**3. 画面一覧テーブル（必須）**

全画面をテーブルで整理する。
名前を並べるだけは禁止。** 1行ごとに「役割」「頻度」「重要度」を書く。**

```
| ID | 画面名           | カテゴリ     | 役割・目的                                      | 利用頻度 | 重要度 |
|----|------------------|--------------|-------------------------------------------------|----------|--------|
| S1 | スプラッシュ     | エントリー系 | ロゴ表示＋初期ロード。初回のみ簡易オンボ案内。 | 低       | 中     |
| S2 | ログイン         | エントリー系 | メール/SNSでログイン。パスワードリセット導線を含む。 | 低（都度） | 高   |
| S3 | サインアップ     | エントリー系 | 新規アカウント登録。                            | 低       | 高     |
| C1 | ホーム           | コア体験系   | 今日やるべき1アクションへの入口。              | 高       | 最重要 |
| C2 | 入力画面         | コア体験系   | テキスト/音声などのインプット。                | 高       | 最重要 |
| C3 | 結果・フィードバック画面 | コア体験系 | AI結果＋次の一手を提示。                        | 高       | 最重要 |
| C4 | 履歴一覧         | コア体験系   | 過去の記録/生成物の一覧・検索。                | 中       | 高     |
| C5 | 履歴詳細         | コア体験系   | 個別の記録/生成物の詳細表示・編集。             | 中       | 高     |
| P1 | プロフィール     | サポート系   | 名前・アイコン・基本設定。                      | 低       | 中     |
| P2 | 課金・プラン画面 | サポート系   | サブスク/チケットの購入・確認。                | 中       | 高     |
| P3 | 設定             | サポート系   | 通知・テーマ・その他細かい調整。               | 低       | 中     |
| M1 | 使い方ガイド（モーダル） | エントリー系 | 初回オンボーディングの補足ツアー。フルスクリーン画面ではなくオーバーレイ表示。 | 低（初回のみ） | 中 |
| Y1 | エラー共通画面   | システム系   | 通信失敗・サーバ障害時の案内＋再試行。          | 低       | 中     |
```

※ 実プロダクト用に行を増やしていけばOK。
※ "重要度" は 「削る候補から逆算」するために書く。
※ 上記で **合計13画面**。「1. 画面数の"予算"」で定めた上限（8〜12画面、13画面超で要再検討）の境界に到達している。M1（モーダル）はオーバーレイでルート遷移を伴わないため実質的な負荷は低いが、予算消化の意識は持っておくこと。今後画面を追加する場合は既存画面の統合を先に検討する。
※ この表のIDは「UIルーティング設計 5. 画面IDとの対応表」「UIワイヤーフレーム設計 3. 画面別ワイヤーフレーム定義」と完全に一致させること。片方だけ更新して他方が古いまま、が一番事故る。
※ `/legal`（利用規約・プライバシー）は静的コンテンツのため画面ID管理の対象外とする（フッター等からの直リンクで完結し、遷移ルールに縛られない）。

⸻

**4. 画面遷移の原則**

画面数だけでなく、「どう繋がるか」も最低限ここで縛る。

- **ホーム（C1）を中心にスター型に構成する。**
- ホーム → 入力 → 結果 → ホーム に最短で戻れること。
- 階層は **最大3階層まで**：
  - 例：ホーム → 履歴一覧 → 履歴詳細
- サポート系画面（設定・課金・ヘルプ等）は
  - すべて「ホーム or プロフィール」から行ける
  - かつ「1タップで戻れる」こと。

ここに簡単な文章で書く：
- メインフロー：
  - ホーム → 入力 → 結果 → ホーム
- サブフロー：
  - ホーム → 履歴一覧 → 履歴詳細 → ホーム
  - ホーム → プロフィール → 課金画面 → ホーム

⸻

**5. 画面削減ルール（No Mercy）**

- 同じデータを **別レイアウトで見せるだけ** の画面は原則作らない。
  → タブ切り替えやフィルタで対応
- 「説明」「使い方」だけの画面は極力作らない。
  → 必要ならモーダル or ツアーで済ませる
- 週1回も開かれない機能は：
  - メニューから削除、もしくは別モード／別アプリ候補に。
  

⸻

## ✅ 機能選出（改訂案 v10）

**0. このセクションの役割**

ゴールはシンプル：
- **「このアプリは、最低限これだけあれば成立する」**
- **「それ以外は、どの順番で後回しにするか」**
- つまりここは、
  **要件定義 × 優先度付け × フェーズ分割** をひとまとめにする場所。

⸻

**1. 機能選出の基本方針**

1. **コア体験ループを支えるかどうか**
   - 支えない機能は「後回し or 別アプリ候補」。
2. **画面構成との対応が取れているか**
   - どの機能が、どの画面で使われるかが言えない機能は禁止。
3. **マネタイズに関係するかどうか**
   - 「お金になる / 継続につながる」機能を優先。
4. **運用コストの低さ**
   - リリース後も自分一人で回せるか？

ここに1〜2行で方針を書く：

例）
「コア体験（入力→生成→振り返り）に直結しない機能は、すべてv2以降に送る。
v1は"毎日の1アクションが気持ちよく回ること"だけに集中する。」

⸻

**2. コア機能 / 補助機能 / 装飾機能**

まず、「役割」でバッサリ切る。

**2-1. コア機能（アプリの存在意義）**

これが無いとアプリの意味が消える機能。
v1リリースまでに **絶対に** 完成させる。

例（フォーマットだけ）：
- F-CORE-01: 入力機能（テキスト / 音声 / 画像 等）
- F-CORE-02: AI処理（生成 / 添削 / 解析）
- F-CORE-03: 結果表示（フィードバック・要約・次アクション提示）
- F-CORE-04: 履歴保存・閲覧

**2-2. 補助機能（継続と快適性を支える）**

無くても死なないが、あると使い続けたくなるやつ。

- F-SUB-01: 検索 / フィルタ / タグ付け
- F-SUB-02: 通知（リマインド）
- F-SUB-03: 成長サマリー（週次・月次のまとめ）
- F-SUB-04: 簡易シェア（Twitter等への共有）

**2-3. 装飾機能（世界観・楽しさ・ブランド）**

「あったら嬉しい」「世界観を育てる」側。

- F-DECOR-01: テーマ変更（ダークモード・カラーセット）
- F-DECOR-02: キャラクター演出（セリフ・リアクション）
- F-DECOR-03: 実績バッジ・称号

⸻

**3. 機能優先度（MoSCoW＋現実）**

M / S / C / W を付ける。
ただし甘え禁止。Must多すぎたらやり直し。

- **Must**: v1で必須。ないとアプリ崩壊。
- **Should**: v1.1〜v2で入れたい。コア体験の質を上げるもの。
- **Could**: チャンスあれば入れる。無くても困らない。
- **Won't (for now)**: 少なくとも半年〜1年はやらない。

テーブルに落とす：

```
| ID         | 機能名                     | 種別      | 優先度 | 概要                                     |
|------------|----------------------------|-----------|--------|------------------------------------------|
| F-CORE-01  | 入力（テキスト）           | コア      | Must   | 1タップで入力開始、送信でAI処理に渡す。 |
| F-CORE-02  | AI生成・解析               | コア      | Must   | OpenAI APIを叩いて結果を受け取る。     |
| F-CORE-03  | 結果表示＋次アクション提示 | コア      | Must   | 結果＋「次にやる1手」を提示する。      |
| F-CORE-04  | 履歴保存・一覧             | コア      | Must   | DBに保存し、後から一覧閲覧可能。       |
| F-SUB-01   | 履歴詳細・編集             | 補助      | Should | 各履歴を詳細表示・タイトル編集など。   |
| F-SUB-02   | 通知（リマインド）         | 補助      | Should | 1日1回、指定時間にプッシュ。           |
| F-SUB-03   | 週次サマリー生成           | 補助      | Could  | 週1でまとめを生成・表示。              |
| F-DECOR-01 | テーマ変更                 | 装飾      | Could  | ライト/ダークなど見た目切替。          |
| F-DECOR-02 | 実績バッジ                 | 装飾      | Won't  | 連続日数等でバッジ付与（当面やらない） |
```

⸻

**4. リリースフェーズ別の機能セット**

「全部できたらリリース」じゃ一生出ない。
フェーズごとに **"どの時点で外に出すか"** を固定する。

**4-1. v1（MVP）**

- 目的：
  - コア体験ループが **ノーストレスで回るか** を検証する。
- 機能セット：
  - Must のみ（＋最低限の Should 1〜2個まで）

**4-2. v1.1〜v1.x**

- 目的：
  - 使いづらさの解消・継続率の改善。
- 機能セット：
  - Should を順次追加
  - ログを見て「明らかに触られてる部分」を強化

**4-3. v2 以降**

- 目的：
  - ブランド・世界観・単価アップ。
- 機能セット：
  - Could / 一部のDecor
  - マネタイズ強化（有料向けの追加価値）

ここに実際のプロダクトでの割り当てを書いていく感じ。

⸻

**5. 画面との対応関係**

「この機能はどの画面から使えるの？」が説明できない機能は切る。

簡単な対応表を作る：

```
| 機能ID     | 機能名                     | 主な利用画面ID |
|------------|----------------------------|----------------|
| F-CORE-01  | 入力（テキスト）           | C1: ホーム, C2: 入力画面 |
| F-CORE-02  | AI生成・解析               | C2: 入力画面  |
| F-CORE-03  | 結果表示＋次アクション提示 | C3: 結果画面  |
| F-CORE-04  | 履歴保存・一覧             | C4: 履歴一覧  |
| F-SUB-02   | 通知（リマインド）         | P3: 設定      |
| F-DECOR-01 | テーマ変更                 | P3: 設定      |
```

ここで「画面も機能も増やしすぎてないか」をチェックする。

⸻

**6. 機能削除・棚上げルール（No Mercy）**

- **3ヶ月以上、ほぼ触られてない機能**
  → ログを見て削除候補入り。
- **実装コストの割に、UX / マネタイズに寄与していない機能**
  → v2以降に送る or そもそもやらない。
- 新機能を1つ追加する時は、
  → 既存機能から1つ「棚上げ候補」を決める。

「機能を増やす時は、画面数とAPI数もセットで増える」
ここをなめると、あとで全リファクタで死ぬ。
  
⸻

## ✅ UIルーティング設計（改訂案 v10）

**0. このセクションの役割**

目的はシンプル：
- **「ユーザーが、どの順番でどの画面に辿り着くか」** を
  コードに落とせるレベルで定義すること。
- 単なる画面遷移図ではなく、
  - ルート構造
  - 認証ガード
  - 戻る動作
  - ディープリンク・通知からの遷移
  まで含めて「ルール」を決める。

⸻

**1. ナビゲーションの基本構造**

まず、アプリ全体を 3つのスタック に分解する。

1. **Authスタック**（未ログインユーザー用）
2. **Mainスタック**（通常利用）
3. **Modal / Overlayスタック**（一時的な画面）

ここに自分のアプリ前提で書く：

```
- Authスタック
  - `/welcome`（初回のみ）
  - `/login`
  - `/signup`

- Mainスタック
  - `/`（ホーム / C1）
  - `/history`（履歴一覧 / C4）
  - `/history/:id`（履歴詳細）
  - `/profile`（プロフィール）
  - `/settings`（設定）
  - `/billing`（課金・プラン）

- Modal / Overlayスタック
  - `/onboarding-guide`（使い方ガイド／チュートリアル）
  - `/legal`（利用規約・プライバシー：モーダル or 別画面）
```

※ Webならパス、モバイルなら Route.Home / Route.Login みたいな名前に置き換えればOK。

⸻

**2. ルート命名規則**

中途半端な命名は後から地獄になる。最初に縛る。

**2-1. ルートID**

R-カテゴリ-連番 で振る：

```
- R-AUTH-01: /welcome
- R-AUTH-02: /login
- R-AUTH-03: /signup

- R-MAIN-01: /          （ホーム）
- R-MAIN-02: /history   （履歴一覧）
- R-MAIN-03: /history/:id
- R-MAIN-04: /profile
- R-MAIN-05: /settings
- R-MAIN-06: /billing

- R-MODAL-01: /onboarding-guide
- R-MODAL-02: /legal（画面ID管理対象外。静的コンテンツ。詳細は「画面数・画面構成」参照）

- R-SYS-01: /error
```

**2-2. パラメータ・クエリのルール**

- パスパラメータ：**必須の識別子**
  - 例：/history/:id
- クエリパラメータ：**絞り込み・状態**
  - 例：/history?filter=favorite

IDをパス、状態をクエリ。逆転禁止。

⸻

**3. 認証ガードと遷移ルール**

ここがフワっとしてるとバグの温床になる。

**3-1. アクセス制御**

ルートごとに「認証必須かどうか」を明記する：

```
| Route ID   | Path            | 要ログイン | 備考                          |
|-----------|-----------------|-----------|-------------------------------|
| R-AUTH-01 | /welcome        | 不要      | ログイン済なら / にリダイレクト |
| R-AUTH-02 | /login          | 不要      | ログイン済なら / にリダイレクト |
| R-AUTH-03 | /signup         | 不要      | 同上                         |
| R-MAIN-01 | /               | 必要      | ホーム                        |
| R-MAIN-02 | /history        | 必要      |                               |
| R-MAIN-03 | /history/:id    | 必要      |                               |
| R-MAIN-04 | /profile        | 必要      |                               |
| R-MAIN-05 | /settings       | 必要      |                               |
| R-MAIN-06 | /billing        | 必要      | サブスク・課金関連           |
| R-MODAL-01| /onboarding-guide | 必要/不要 | 初回のみ自動表示も検討      |
| R-MODAL-02| /legal          | 不要      | 静的コンテンツ。未ログインでも閲覧可 |
| R-SYS-01  | /error          | 不要      | 致命的エラー時の共通遷移先。認証状態を問わず表示可能 |
```

**3-2. ガードの挙動**

- 未ログインで Main系ルートにアクセスした場合：
  - /login にリダイレクト
  - ログイン完了後、**元のルートへ戻す**（next パラメータで管理）
- ログイン済ユーザーが /login / /signup に来た場合：
  - / へリダイレクト

⸻

**4. 主要フローのルーティング**

**4-1. 起動〜コア体験まで**

最低限、これだけは文章で固定しておく：

```
- 初回起動：
  - スプラッシュ → /welcome → /signup or /login → /onboarding-guide → /
- 2回目以降：
  - スプラッシュ → 認証チェック → ログイン済なら `/`、未ログインなら `/login`
```

**4-2. コア体験ループの遷移**

UXセクションで決めたコアループを、ルートで再定義：

```
1. `/`（ホーム：今日の一手を提示）
2. `/input`（※あれば。なければホーム内セクション）
3. `/result`（生成結果・フィードバック）
4. `/`（ホームへ戻る＋「次の一手」提示）
```

※ /input / /result を別画面にするか、ホームの中のセクションにするかはプロダクト次第。
　どっちにするかここでハッキリ書く。

⸻

**5. 画面IDとの対応表**

画面設計とルーティングがズレないように、対応表を作る。

```
| Route ID   | Path            | 画面ID | 画面名                 |
|-----------|-----------------|--------|------------------------|
| R-AUTH-01 | /welcome        | S1     | ウェルカム             |
| R-AUTH-02 | /login          | S2     | ログイン              |
| R-AUTH-03 | /signup         | S3     | サインアップ          |
| R-MAIN-01 | /               | C1     | ホーム                |
| R-MAIN-02 | /history        | C4     | 履歴一覧              |
| R-MAIN-03 | /history/:id    | C5     | 履歴詳細              |
| R-MAIN-04 | /profile        | P1     | プロフィール          |
| R-MAIN-05 | /settings       | P3     | 設定                  |
| R-MAIN-06 | /billing        | P2     | 課金・プラン          |
| R-MODAL-01| /onboarding-guide | M1   | 使い方ガイドモーダル  |
| R-SYS-01  | /error          | Y1     | エラー共通画面        |
```

※ R-MODAL-02（/legal）は静的コンテンツにつき画面IDを割り当てない（「画面数・画面構成」参照）。
※ この表は「画面数・画面構成 3. 画面一覧テーブル」と1対1で揃っていることを都度確認する。

⸻

**6. 通知・ディープリンク時のルーティング**

通知や外部リンクから来たときの挙動をここで固定する。

**6-1. 通知タップ**

例：
- 「今日の一手」通知
  → /（ホーム）を開き、?focus=today で該当セクションを強調
- 「◯◯の記録を振り返ろう」通知
  → /history/:id へ遷移

**6-2. ディープリンク**

- myapp://history/:id → /history/:id（未ログインならログイン経由）
- myapp://billing → /billing

未ログイン時に叩かれたら必ず /login?next=/history/:id みたいに戻り先を保持する。

⸻

**7. ローディング・エラー時のUIルート**

「通信中」「サーバエラー」もルーティングレベルでルール化する。

- ローディングは **専用画面ではなく、基本は各画面内のオーバーレイ** で対応。
  （ルートを増やさない）
- ただし、本当に何も出せない初期ロード（起動直後）だけは例外で以下を使う：
  - /initial-loading（スプラッシュ兼ねても良い）

エラー時：
- APIエラー：
  - 各画面内でトースト or インラインエラーメッセージ
- 致命的エラー：
  - 共通のエラー画面：/error（R-SYS-01）に遷移
  - そこから / に戻るボタン

⸻

**8. No Mercy ルール（UIルーティング編）**

最後に縛りを明文化する。

- 階層は **3段まで**
  例：/history → /history/:id → 編集モーダル
  「設定の中の設定の中の設定」みたいなのは禁止。
- 同じデータを別URLで出すな：
  - /history/:id と /records/:id で同じ中身 → どっちかに統一。
- モーダル乱発禁止：
  - 「閉じるボタンが多い」アプリはうざい。
  本当に"サッと出てサッと消えたい"ものだけモーダル。
- ログイン動線は1本にまとめる：
  - /signup から途中 /login に飛ばして戻れなくなる、みたいなクソ動線はNG。
- 新ルートを増やすときは：
  - 既存ルートのどれかを「縮小 or 統合」する前提で追加する。
  

⸻

## ✅ UIワイヤーフレーム設計（改訂案 v10）

**0. このセクションの役割**

ゴール：
- **「各画面で、何がどこにどの優先度で置かれるか」** をテキストで定義すること。
- ここはアートじゃない。
  デザイナー不在でも、エンジニアが
  **「縦にこれ、次にこれ」で UI を組める** ところまで分解する。

⸻

**1. ワイヤーフレームの共通ルール**

**1-1. 解像度（Lo-Fi 固定）**

- カラー・フォント・アイコンの細かい話はここではやらない。
- 定義するのは：
  - ブロック構造（ヘッダー / コンテンツ / フッター 等）
  - コンポーネントの種類（ボタン / リスト / カード / フォーム など）
  - 優先度（どこが一番目立つべきか）

**1-2. レイアウトの原則**

- スマホ前提：**縦 1 カラム** を基本とする。
- 横スクロールやタブを使うときは「なぜ横にしたか」を書く。
- 1画面の中で「視線の流れ」が上から下に自然につながるようにする：
  1. ページタイトル / 状態サマリ
  2. メインのアクション
  3. セカンダリアクション
  4. 補足情報

⸻

**2. 共通レイアウト / コンポーネント定義**

まずは全画面で使い回す「型」を固定する。

**2-1. ベースレイアウト**

```
- ヘッダー
  - 左：戻る or ハンバーガー or ロゴ
  - 中央：画面タイトル
  - 右：サブアクション（設定、ヘルプ等）

- コンテンツエリア
  - 上：状態サマリ or タブ
  - 中：メインコンテンツ（リスト / フォーム / 結果表示）
  - 下：メインアクションボタン or FAB

- フッター（必要な場合のみ）
  - ボトムナビ or コピーライト等
```

**2-2. 共通コンポーネント**

ここに「再利用前提の部品」を列挙する。

- ボタン：
  - **Primary**：画面の主目的（例：送信 / 保存 / 次へ）
  - **Secondary**：戻る / キャンセル / その他
- カード：
  - リスト用の1アイテム型（タイトル / サブテキスト / メタ情報）
- 入力：
  - テキストフィールド（単一行 / 複数行）
  - トグル / スイッチ / セレクト
- ステータス：
  - ローディングインジケータ
  - 空状態メッセージ
  - エラーバナー or トースト

このコンポーネント名は、実際の UI 実装（React コンポーネント名 等）と揃えておくと後々ラク。

⸻

**3. 画面別ワイヤーフレーム定義**

ここがメイン。
**画面IDごとに、レイアウトとコンポーネントを言語化する。**

フォーマットはこれで統一しろ：

```
#### C1: ホーム画面（UIワイヤーフレーム）

- 画面の目的
  - 例）「今日やるべき1アクションを一発で提示し、そこからすぐ入力に入れること」

- 主要ユーザーアクション
  - A1: 今日の一手を実行する（Primary）
  - A2: 履歴に飛ぶ
  - A3: プロフィール / 設定にアクセス

- レイアウト構造（上から順）
  1. ヘッダー
     - 左：メニューボタン（プロフィール or ドロワー）
     - 中央：アプリタイトル or 「今日の一手」
     - 右：通知アイコン（タップで通知設定画面へ）
  2. 状態サマリエリア
     - 「◯日連続」「今月の記録数」などのミニカード
  3. メインアクションエリア
     - 「今日の一手」カード
       - タイトル（今日のテーマ）
       - サブテキスト（ひと言説明）
       - Primaryボタン：`今すぐやる`
  4. セカンダリアクションエリア
     - ボタン：`履歴を見る`
     - ボタン：`過去のハイライト`
  5. フッター or ボトムナビ（必要な場合）
     - ホーム / 履歴 / プロフィール の3タブ

- 状態別バリエーション
  - 通常：上記レイアウト
  - 初回 / データ0件：
    - 状態サマリエリアを「ようこそカード」に差し替え
    - 「まずは1件登録してみよう」などの導線文言
  - ローディング：
    - メインアクションエリアにスケルトン表示
  - エラー：
    - 画面上部にエラーバナー、再試行ボタン
```

同じフォーマットで、他の画面IDも書く：
- C2: 入力画面
- C3: 結果画面
- C4: 履歴一覧
- C5: 履歴詳細
- P1: プロフィール
- P2: 課金・プラン
- P3: 設定
…など、画面数セクションで定義した ID に対応させる。

⸻

**4. 状態（State）ワイヤーフレームの扱い**

一番サボりがちで、一番ユーザー体験を壊すところ。

各画面について最低限この4つに触れる：
1. **通常状態（Normal）**
2. **ローディング（Loading）**
3. **空状態（Empty）**
4. **エラー（Error）**

**4-1. Empty のルール**

- ただの「データがありません」は禁止。
- 代わりに：
  - なぜ空か（初回だから / フィルタがきついから）
  - 次に何をすべきか（ボタン1つ）

例：履歴画面の Empty

```
- アイコン（シンプル）
- メッセージ：「まだ記録がありません」
- サブテキスト：「今日の一手から始めてみましょう」
- ボタン：「ホームに戻る」
```

**4-2. Error のルール**

- 画面全体を真っ白にせず、**可能な限り前の内容は見せたまま**。
- 最低限：
  - 何が起きたか
  - ユーザーができること（再試行 / 戻る）

⸻

**5. レスポンシブ / マルチデバイス方針（必要なら）**

もし PC / タブレットも視野に入れるなら、ここでルールを書く。

- スマホ：
  - 縦 1 カラムベース
- タブレット：
  - 一覧＋詳細の 2 カラム（例：左がリスト、右が詳細）
- PC：
  - サイドバー / ヘッダーのナビゲーション

ただし、個人開発で最初から全部やるのは自殺行為。
v1 はスマホ前提だけ明確に書いておけば十分。

⸻

**6. UIワイヤーと他セクションとの紐付け**

各画面定義の中で、以下を明示しておく：
- 対応する **画面ID**（画面数セクション）
- 対応する **Route ID**（UIルーティング設計）
- 主に使う **機能ID**（機能選出）

例：

```
- 対応画面ID: C1（ホーム）
- 対応Route: R-MAIN-01 `/`
- 主に関わる機能:
  - F-CORE-01 入力起点
  - F-CORE-04 履歴一覧への導線
  - F-SUB-02 通知への導線（設定へ）
```

こうしておくと、実装時に
「この画面触るときに、どのAPI / どの機能に影響出るか」が一目で分かる。

⸻

**7. No Mercy ルール（UIワイヤー編）**

最後に縛り条件だ。

- 1画面1目的：
  - 「やることが3つ以上ある画面」はほぼ失敗。
  → メインアクションは常に1つに絞れ。
- テキスト詰め込み禁止：
  - スマホで **3スクロール超える説明文** は読まれない。
- 装飾より優先：
  - 「世界観」より先に、「どのボタンを押せばいいか」が一瞬でわかること。
- 無駄な余白恐怖症を捨てろ：
  - ぎっちぎちに詰めた UI は、結果的に"何も見えない"のと同じ。
- 新しい画面を増やすときは：
  - 既存画面のどれかから要素を削る or 統合する前提で。  
  
⸻

## ✅ API設計（改訂案 v10）

**0. このセクションの役割**

ゴール：
- **「フロントから見たとき、APIがどう見えるか」** を統一ルール込みで定義する。
- ここで決めるのは：
  - APIレイヤーの構成（Backend / BFF / 外部API）
  - エンドポイント構造（リソース・URL命名・HTTPメソッド）
  - 認証・認可・エラー形式
  - ページネーション / フィルタ / キャッシュ方針
  - 詳細な型定義（OpenAPI/Schema）は別ファイルでOK。
ここは **思想＋一覧＋ルール** に絞る。

⸻

**1. APIレイヤー構成**

まず、「APIをどこでどう提供するか」を決める。

```
- Backend API
  - ベースURL例：`/api/v1/`
  - Django REST Framework / FastAPI などで提供
  - 主に:
    - ユーザー管理
    - ドメインデータ（記録・履歴・設定など）
    - 決済・プラン
    - LLM呼び出しのラッパ

- BFF (Backend for Frontend) ※必要な場合のみ
  - ベースURL例：`/bff/v1/`
  - 特定クライアント用にレスポンス最適化（集約・整形）
  - フロントのための"専用窓口"として使う

- 外部API連携
  - OpenAI, Stripe, OAuthプロバイダ など
  - すべて Backend 内部から呼び出し
  - フロントから直接外部APIを叩くことは ******禁止******
```

原則：
**クライアント → 自前API → 外部API** の一枚挟み構造に固定する。

⸻

**2. リソースモデルと責務**

まずは「どのリソースをAPIで触るか」をテーブルにする。
（実プロダクトに合わせて書き換えろ）

```
| リソース     | 説明                          | 主な操作                      | 対応DBテーブル（DB設計参照） |
|-------------|-------------------------------|-------------------------------|-------------------------------|
| User        | ユーザーアカウント            | 登録 / 認証 / プロフィール   | users, user_profiles          |
| Session/Auth| 認証・トークン                | ログイン / リフレッシュ      | なし（JWTはステートレス。Refresh Token失効管理が必要になったらrefresh_tokensテーブルを別途検討） |
| Entry       | ユーザーの1件分の記録・入力   | 作成 / 取得 / 更新 / 削除    | entries                       |
| History     | Entryの一覧・サマリ           | 検索 / 絞り込み               | entries（専用テーブルなし、entriesへのクエリで表現） |
| Summary     | 週次・月次サマリー            | 生成 / 取得                   | summaries                     |
| Plan        | 課金プラン・サブスク状態      | 確認 / 更新                   | plans, subscriptions          |
| Billing     | 課金トランザクション          | 作成 / 確認 / Webhook受信    | billing_events, subscriptions |
| LLMSession  | LLMへの問い合わせログ         | 作成 / 取得                   | generated_contents            |
| Setting     | 通知・テーマなどのユーザー設定| 取得 / 更新                   | user_settings                 |
```

ここに **「UI画面」「機能ID」と1対1 or 1対多で対応するリソース** を並べる。

※ DB側には他に `notifications`（通知配信履歴）と `audit_logs`（監査ログ）があるが、これらは内部処理専用でREST APIリソースとしては公開しない想定。意図的な非対応なので、ここに明記して「書き漏れ」と区別する。

⸻

**3. エンドポイント設計の基本ルール**

**3-1. バージョニング**

- ベースURLにバージョンを含める：
  - 例：/api/v1/...
- v1で公開したものは **極力壊さない**。
  壊す必要が出たら /api/v2/ を切る。

**3-2. URL命名規則**

- 名詞の複数形を基本とする：
  - /entries, /users, /plans
- 単一リソース：
  - /entries/{id}
- サブリソース：
  - /entries/{id}/comments
  - /users/me/settings

**3-3. HTTPメソッド**

- GET：取得
- POST：新規作成 / 特別アクション
- PUT：全体更新
- PATCH：部分更新
- DELETE：削除

「なんでもPOST」はやめろ。
メソッドの意味をごまかすと、あとで自分が困る。

⸻

**4. 代表エンドポイント一覧**

（例。実際はプロダクトに合わせて書き換え）

```
#### ユーザー・認証

- POST   `/api/v1/auth/signup`      : ユーザー登録
- POST   `/api/v1/auth/login`       : ログイン（JWT発行など）
- POST   `/api/v1/auth/refresh`     : アクセストークン更新
- POST   `/api/v1/auth/logout`      : ログアウト
- GET    `/api/v1/users/me`         : 自分のプロフィール取得
- PATCH  `/api/v1/users/me`         : 自分のプロフィール更新

#### 記録 / エントリ

- GET    `/api/v1/entries`          : 自分のEntry一覧（クエリでフィルタ）
- POST   `/api/v1/entries`          : 新規Entry作成
- GET    `/api/v1/entries/{id}`     : Entry詳細
- PATCH  `/api/v1/entries/{id}`     : Entry更新
- DELETE `/api/v1/entries/{id}`     : Entry削除

#### サマリー / 履歴

- GET    `/api/v1/history/daily`    : 日次一覧
- GET    `/api/v1/history/weekly`   : 週次サマリー
- GET    `/api/v1/history/monthly`  : 月次サマリー

#### 設定

- GET    `/api/v1/settings`         : 設定取得
- PATCH  `/api/v1/settings`         : 設定更新（通知ON/OFFなど）

#### 課金・プラン

- GET    `/api/v1/plans`            : 提供中プラン一覧
- GET    `/api/v1/billing/status`   : ユーザーの契約状態
- POST   `/api/v1/billing/subscribe` : サブスク開始
- POST   `/api/v1/billing/cancel`   : サブスク解約
- POST   `/api/v1/billing/webhook`  : Stripe等からのWebhook受信

#### LLM連携

- POST   `/api/v1/llm/analyze-entry`  : Entryを解析・生成
- POST   `/api/v1/llm/generate-summary` : サマリー生成
```

⸻

**5. リクエスト / レスポンス形式**

**5-1. 共通ルール**

- 形式：JSON固定
- 時刻：ISO8601（UTC or タイムゾーン付き）
- 文字コード：UTF-8

**5-2. レスポンスラッパ方針**

どっちかに統一しろ：

1. **ラップあり** パターン（おすすめ）

```
{
  "success": true,
  "data": { ... },
  "error": null
}
```

2. **ラップなし** パターン
リストならそのまま [{...}, {...}] を返す方式。

中途半端に混在させるのだけは絶対やめろ。
個人開発でも「揃ってるかどうか」で future 自分の生産性が変わる。

**5-3. エラー形式**

共通の error オブジェクトを定義する：

```
{
  "success": false,
  "data": null,
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "入力値に誤りがあります。",
    "details": {
      "field_errors": {
        "title": ["この項目は必須です。"]
      }
    }
  }
}
```

⸻

**6. 認証・認可**

**6-1. 認証方式**

- SPA / モバイル：
  - JWT + Refresh Token
  - HTTPヘッダ：Authorization: Bearer <token>
- SSR / 通常Web：
  - セッション＋Cookie＋CSRFトークン（Django標準）

**6-2. 権限レベル**

- user：通常ユーザー
- admin：管理者（管理画面専用APIのみ）
- 一般APIは基本 user 前提。
  管理系は /api/v1/admin/... に分離する。

⸻

**7. ページネーション / フィルタ / ソート**

**7-1. ページネーション方式**

- クエリパラメータ例：
  - ?page=1&limit=20
- レスポンス例：

```
{
  "success": true,
  "data": {
    "items": [ ... ],
    "meta": {
      "page": 1,
      "limit": 20,
      "total_items": 153,
      "total_pages": 8
    }
  },
  "error": null
}
```

**7-2. フィルタ・検索**

- クエリパラメータで統一：
  - ?q=（キーワード）
  - ?from=YYYY-MM-DD&to=YYYY-MM-DD
  - ?tag=xxx
- 「複雑な検索条件」は v1 では作り込まない。
  必要性が出てからでいい。

**7-3. ソート**

- ?sort=created_at
- 降順は：?sort=-created_at のように prefix を決めておく。

⸻

**8. ステータスコードの使い分け**

最低限これだけは守れ：

- 200 OK：正常
- 201 Created：新規作成
- 204 No Content：削除や更新後、返すものがない時
- 400 Bad Request：バリデーション失敗
- 401 Unauthorized：認証エラー
- 403 Forbidden：権限不足
- 404 Not Found：リソースが無い
- 409 Conflict：競合（重複登録など）
- 429 Too Many Requests：レート制限
- 500 Internal Server Error：サーバエラー

全部200で返すのは、ただの怠慢だと思え。

⸻

**9. パフォーマンス・キャッシュ・レート制限**

**9-1. キャッシュ**

- 読み取り中心のエンドポイント（例：プラン一覧など）は
  - サーバー側キャッシュ（Redis） or HTTPキャッシュ
- LLMの結果も、再利用可能ならキャッシュ候補。

**9-2. レート制限**

- 認証 API（login 等）に対しては、IPベースでレート制限。
- LLM連携 API もトークン消費を守るため制限を入れる：
  例）
  - /llm/analyze-entry: ユーザーごとに 1分間 X回まで

⸻

**10. トランザクション・冪等性（特に課金）**

- 課金系 API (/billing/...) は **冪等性キー** を使う：
  - ヘッダ：Idempotency-Key: <uuid>
- サーバー側は同じキーの重複リクエストに対して同じ結果を返す。

「二重決済」やったら一発アウトだと思って設計しろ。

⸻

**11. ログ / 監視 / デバッグ**

- すべてのAPIリクエスト：
  - path / method / user_id / status / duration をログに残す。
- LLM連携系：
  - プロンプト・レスポンスを丸ごとではなく、
    **要約＋トークン数** くらいに圧縮して保存（コストとプライバシ的に）。

⸻

**12. No Mercy ルール（API編）**

- 新しいエンドポイントを増やす前に：
  - 「既存のリソースで表現できないか？」を考えろ。
- 複数のエンドポイントが、ほぼ同じデータを返している場合：
  - どれか1つに統合＋クエリパラメータで表現する。
- 「いったん仮のURLで」は禁止：
  - 仮URLは一生そのまま残る。
  → 最初からちゃんと名前をつけろ。
- v1では「使われないであろう汎用性」を目指すな：
  - まずは **実際に使う画面と機能だけ** サポートすればいい。
  
⸻  

## ✅ DB設計（改訂案 v10）

**0. このセクションの役割**

ゴール：
- **「このプロダクトのデータは、何を・どこまで・どう持つか」** を決めること。
- ここで決めるのは：
  - 主要テーブルと関係（ERの骨格）
  - 命名規則・正規化方針
  - インデックス・ユニーク制約
  - 監査ログ・削除戦略（物理 / 論理）
  - ここは "図が描けるだけ" じゃ不十分。
**SQLを書けるレベルまで粒度を落とす。**

⸻

**1. 全体方針**

**1-1. 使用DBと理由**

- 使用DB：PostgreSQL
- 理由：
  - JSONB・拡張性
  - 型がしっかりしている
  - Render等との相性
  - 将来の集計・分析にも耐えやすい

**1-2. 正規化方針**

- 基本：**第3正規形** までは守る
- ただし：
  - 重い集計や履歴は、必要に応じて「集計テーブル」「マテビュー」で**意図的に冗長化**可
  - 「最初からなんでもJSONBに突っ込む」は禁止。

**1-3. マルチテナント方針（必要なら）**

- 単一アプリ＆個人開発前提：
→ **テナント分割はせず、user_id でスコープ管理**
- 将来B2Bマルチテナントにするなら：
  - tenant_id カラムを全テーブルに持たせる or DB分割案を別途検討  
  
⸻

**2. 主要テーブル一覧（ER骨格）**

**※ 実プロダクトに応じて名前変えろ。例として出す。**

```
| テーブル名           | 役割                                  |
|----------------------|---------------------------------------|
| users                | ユーザーアカウント                   |
| user_profiles        | プロフィール・公開情報               |
| entries              | ユーザーの1件分の入力・記録          |
| generated_contents   | LLM等で生成されたテキスト/結果       |
| summaries            | 週次・月次サマリ                     |
| user_settings        | 通知・テーマなどの設定               |
| plans                | 提供プラン（Free / Pro 等）          |
| subscriptions        | ユーザーごとの契約情報               |
| billing_events       | 課金イベント（Stripe等のWebhook）    |
| notifications        | 通知キュー・履歴                     |
| audit_logs           | 監査ログ（重要操作の履歴）           |
```

ポイント：
コアは **users / entries / generated_contents / subscriptions**。
他は補助。

⸻

**3. 命名規則 & 共通カラム**

**3-1. 命名**

- テーブル：**スネークケース複数形**
  - users, user_profiles, generated_contents
- カラム：
  - 外部キー：<参照テーブル単数形>_id（例：user_id）
  - 日付：*_at（created_at, updated_at, deleted_at）

**3-2. 共通カラム**

ほぼ全テーブルに入れる：

- id (PK, bigserial or UUID)
- created_at (作成日時, timestamptz)
- updated_at (更新日時, timestamptz)

論理削除したいテーブルには：

- deleted_at (null許可)
→ null = 有効, not null = 削除済み  
  
⸻

**4. テーブル定義（代表例）**

**4-1. users**

```
users

- id            : PK
- email         : ユニーク, 必須
- password_hash : ハッシュ
- is_active     : bool, default true
- is_admin      : bool, default false
- created_at    : timestamptz
- updated_at    : timestamptz

制約：
- email UNIQUE
- is_active による論理無効化
```

**4-2. user_profiles**

```
user_profiles

- id          : PK
- user_id     : FK → users.id (1:1)
- display_name: 表示名
- avatar_url  : アイコンURL
- locale      : 言語設定
- timezone    : タイムゾーン
- created_at
- updated_at

制約：
- user_id UNIQUE（1ユーザー1プロフィール）
```

**4-3. entries（コア）**

```
entries

- id           : PK
- user_id      : FK → users.id
- content_type : 種別（例：text / voice / etc）
- raw_content  : 元入力（テキスト）
- metadata     : JSONB（音声ファイルパス, 長さ, etc）
- created_at
- updated_at
- deleted_at   : 論理削除用（必要なら）

インデックス：
- user_id, created_at の複合INDEX  
```
  
**4-4. generated_contents（LLM結果）**

```
generated_contents

- id              : PK
- user_id         : FK → users.id
- entry_id        : FK → entries.id, null可（エントリ起点じゃない生成もある）
- content_type    : 種別（correction / summary / story / plan 等）
- title           : 短いタイトル or 見出し
- body            : 生成テキスト本体
- prompt_id       : 使用したプロンプトテンプレID
- prompt_version  : "v1" など
- model_name      : "gpt-5.1-mini" 等
- input_tokens    : int
- output_tokens   : int
- feedback_score  : smallint, null可（👍=1 / 👎=-1 など）
- created_at
- updated_at

インデックス：
- user_id, content_type
- entry_id
```

**4-5. summaries（週次・月次サマリ）**

```
summaries

- id           : PK
- user_id      : FK → users.id
- period_type  : "weekly" / "monthly"
- period_start : date
- period_end   : date
- title        : 件名的なタイトル
- body         : サマリ本文
- meta         : JSONB（集計値など）
- created_at
- updated_at

ユニーク制約：
- (user_id, period_type, period_start, period_end)
```

**4-6. user_settings**

```
user_settings

- id                   : PK
- user_id              : FK → users.id
- notify_daily         : bool
- notify_weekly        : bool
- notify_time          : time, null可
- theme                : "light" / "dark" / "system"
- language             : "ja" / "en" など
- created_at
- updated_at

ユニーク：
- user_id UNIQUE
```  
  
**4-7. plans / subscriptions / billing_events**

ざっくり構造：

```
plans
- id           : PK
- code         : "free" / "pro_monthly" 等（UNIQUE）
- name         : 表示名
- price_cents  : 月額/年額など
- currency     : "JPY" 等
- interval     : "month" / "year"
- metadata     : JSONB（Stripe price_id 等）
- is_active    : bool
- created_at
- updated_at

subscriptions
- id             : PK
- user_id        : FK → users.id
- plan_id        : FK → plans.id
- status         : "active" / "cancelled" / "trialing" 等
- started_at
- current_period_end : timestamptz
- canceled_at    : timestamptz, null可
- created_at
- updated_at

billing_events
- id           : PK
- user_id      : FK → users.id
- provider     : "stripe" など
- external_id  : プロバイダ側のID
- event_type   : "invoice.paid" 等
- payload      : JSONB（Webhook丸ごと）
- created_at
```  
  
⸻

**5. インデックス・パフォーマンス方針**

**5-1. インデックス原則**

- 必須：
  - 全FKに対してINDEX付与（user_idなど）
  - よく絞り込む条件（created_at / content_type）に複合INDEX
- 禁止：
  - 「とりあえず全部にINDEX」→ 書き込み遅延＆メモリ食い

例：

- entries(user_id, created_at DESC)
- generated_contents(user_id, content_type)
- summaries(user_id, period_type, period_start)

**5-2. 検索・一覧の想定**

- 一覧画面でのクエリを先に意識：
- 例）
「ユーザーの直近30件のEntry」
→ WHERE user_id = ? ORDER BY created_at DESC LIMIT 30

このレベルでSQLを想像した上でインデックスを貼る。

⸻

**6. 削除戦略（物理 vs 論理）**

**6-1. 論理削除するもの**

- entries / generated_contents / summaries は
→ ユーザーの「記録」なので履歴として価値がある
→ **論理削除（deleted_at）推奨**

論理削除時のルール：

- 通常クエリは WHERE deleted_at IS NULL を必須条件にする
→ ORMのデフォルトManager等で吸収

**6-2. 物理削除でいいもの**

- notifications（送達履歴）
- エラー多発ログ
→ 定期的にクリーンアップバッチで削除

⸻

**7. マイグレーション・バージョニング**

- migrations/ ディレクトリ（Djangoなら標準のやつ）で管理。
- ルール：
  - スキーマ破壊的変更（カラム削除 / 型変更）は
**段階的マイグレーション** を徹底：
    1. 新カラム追加（両方持つ）
    2. コード更新（新カラム読みに切替）
    3. データ移行
    4. 旧カラム削除

直接カラム削除して「本番落ちました」は、ただの自殺。

⸻

**8. セキュリティ・プライバシ**

- パスワード：
  - password_hash のみ（ハッシュ前は保持しない）
- 住所・本名などのセンシティブ情報が必要なら、
→ テーブルを分けて、アクセスを管理者UIのみに限定。
- LLMログ：
  - 生データ全部を保存せず、可能な限り要約 or ハッシュ化
→ プライバシ/コスト両面で守る。

⸻

**9. バックアップとリテンション**

- バックアップ方針：
  - 本番DB：1日1スナップショット（Render等の機能活用）
  - 保持期間：30〜90日程度（サービス規模に応じて）
- 古いデータ：
  - 1年以上触られていないgenerated_contentsなどは
→ 別テーブル / 別ストレージへアーカイブ候補

⸻

**10. No Mercy ルール（DB編）**

- 「とりあえずJSONBに全部突っ込む」は逃げ。
→ 構造が安定してるなら、ちゃんとカラムに切る。
- テーブルを増やす前に：
→ 既存のテーブル＋カラム追加で表現できないか考えろ。
- ER図だけ描いて満足するな：
→ **実際のSELECT文・JOIN文が頭に浮かばない設計はクソ。**
- コアテーブル（users / entries / generated_contents）は
→ スキーマ変更に慎重になれ。
ここコケると全部巻き込んで死ぬ。
- 「とりあえず削除」は禁止：
→ 論理削除を挟んで様子を見てから物理削除。

⸻

## ✅ コンテンツ生成・配信パイプライン設計（改訂案 v10）

**0. このセクションの役割**

ゴール：
- **「コンテンツ（AI生成含む）が、どこから生まれ、どこへ、どう配られるか」** を一本の線で説明できること。
- 対象：
- LLM生成コンテンツ（添削結果、解説、ストーリー、旅程など）
- システムメッセージ（週報・月報・レコメンド）
- マーケティング系配信（通知・メール・SNS用テキスト）

⸻

**1. コンテンツの種類と配信チャネル**

まず、「何を」「どこに」流すかを棚卸しする。

**1-1. コンテンツ種別**

例（プロダクトごとに書き換え）：

- **インタラクティブ生成系**
  - ユーザー入力に対する即時生成
  - 例：英作文の添削、旅プラン生成、株コメント生成 など
- **サマリー / レポート系**
  - 1日 / 1週間 / 1ヶ月単位でまとめる
- **リマインド・ナッジ系**
  - 「今日これやっとけ」「あの記録振り返れ」みたいな軽い文面
- **マーケティング系**
  - メール、SNS投稿、アプリ内お知らせ

**1-2. 配信チャネル**

- **アプリ内表示**
  - 画面上のテキスト / カード / ストーリー
- **プッシュ通知**
  - モバイル / Web Push
- **メール**
  - 週報 / 月報 / キャンペーン
- **外部プラットフォーム**
  - X 投稿用文面生成 etc（今後使うなら）

ここに実プロダクトごとに「どの組み合わせを使うか」を書く。

⸻

**2. 生成パイプラインの共通フロー**

どのコンテンツも、基本この**5ステップで回す：**  
1. **トリガー**
   - ユーザー操作 / スケジュール / イベント発火
2. **入力収集**
   - ユーザー入力 + 過去データ + 設定値をまとめる
3. **生成ロジック**
   - LLM or ルールベースでコンテンツ生成
4. **後処理（Post-process）**
   - トリミング / マスク / フォーマット / スコア付け
5. **保存 & 配信**
   - DB or ストレージに保存し、UI or 通知経由で配る

これを、擬似フローで書いておく：

```
[Trigger] → [InputAssembler] → [LLM/Generator] → [PostProcessor] → [Store] → [Deliver]
```

⸻

**3. LLMベース生成の設計**

**3-1. プロンプト設計とテンプレ管理**

- すべての LLM 呼び出しは「テンプレID＋変数」で管理する：
  - PROMPT_EN_CORRECTION_V1
  - PROMPT_TRIP_PLAN_DAY3_V2
  - テンプレは別ファイル管理（例：prompt-templates.md）

基本方針：
- プロンプトは **1用途1テンプレ**。
「なんでも屋プロンプト」は禁止。
- バージョン管理：
  - …_V1, …_V2 のように suffix で明示
  - どのバージョンを使ったかをログに残す

**3-2. モデル選択とトークン予算**

- 各コンテンツ種別ごとに、
**使用モデルとトークン上限** を決めておく。

例：  
  
```
- インタラクティブ添削:
  - モデル: gpt-5.1-mini
  - 入力: 最大 1,000 tokens
  - 出力: 最大 500 tokens

- 週次サマリー:
  - モデル: gpt-5.1
  - 入力: 最大 4,000 tokens（まとめ前に圧縮）
  - 出力: 最大 1,000 tokens
```

「なんでもとりあえず 5.1 で」はコスト爆死コース。
種別ごとに**明示的に決めておくこと。**

**3-3. セーフティ・フィルタ**

- 不適切なコンテンツのフィルタリング方針を書く：
  - OpenAI 側のセーフティで落ちたときの挙動
  - ユーザー入力がヤバい場合のハンドリング
  - 禁止ワード or NGパターンがあれば事後チェック

⸻

**4. 生成結果の保存・バージョニング**

**4-1. 保存するか、その場だけか**

コンテンツ種別ごとに、以下を決める：

- **保存する**（履歴として残すもの）
  - 添削結果、ストーリー、旅プラン、株コメント 等
- **保存しない**（その場だけ見せる一時結果）
  - 特定のヘルプメッセージ、テスト的生成 等

「全部保存」はやめろ。DBとコストを殺す。

**4-2. 保存構造の基本**

最低限、この3つは保存：

- input_snapshot（LLMに渡した入力要約 or ハッシュ）
- output_text（生成結果）
- meta（モデル名 / トークン数 / prompt_id / version）

これを GeneratedContent 的な共通テーブルとして設けても良い。

⸻

**5. 配信パイプライン（チャネルごとの流れ）**

**5-1. アプリ内表示**

- 原則：生成結果はまずアプリ内で確認させる。
- 画面との対応：
  - 結果画面（C3）
  - 履歴詳細（C5）
  - サマリー画面 など

**UI側ルール：**

- 生成中はスケルトン or ローディング表示
- 完了後、ユーザーに「保存 / 破棄 / 再生成」などの選択肢を出す

**5-2. プッシュ通知・メール**

通知やメールに乗せるパターン：

- 「中身の全文を乗せる」
- 「要約だけを乗せて、詳細はアプリで見る」

後者を基本にする。
通知で全部読ませようとすると UX も計測も崩壊する。

例：

```
- バックエンド側で「通知用テキスト」を別途生成（短文）
- 通知タップで `/summary/weekly` 等の画面へ遷移
```

⸻

**6. バッチ生成 / スケジュール生成**

週次レポート、月次ハイライトみたいなやつ。

**6-1. スケジューラの設計**

- CRON or やるサービス（例：Celery Beat, Render cron）
- 実行タイミング：
  - 週次：日曜 23:00〜24:00
  - 月次：月末 or 月初

**6-2. 処理フロー**

1. 対象ユーザー抽出（一定条件を満たすユーザーだけ）
2. 対象期間のデータ収集
3. LLM用に要約 or 圧縮
4. サマリ生成
5. 保存（Summary テーブル）
6. 通知 or メール配信

ここも「全ユーザーに毎回必ず出す」は危険。
アクティブユーザー or 一定条件以上の利用者だけに絞る前提で。

⸻

**7. ログ・フィードバック・改善ループ**

生成系は作って終わりじゃない。ここからが本番。

**7-1. ログ**

- LLM呼び出しごとに記録：
  - user_id
  - prompt_id / version
  - model
  - input_token / output_token
  - duration
  - success / error
  - コンテンツIDと紐付けて、後から「どのテンプレがどのくらい使われたか」見れるようにする。

**7-2. ユーザーフィードバック**

- 生成結果に対して：
  - 👍 / 👎 / 再生成ボタン
  - Optionalで「一言フィードバック」
  - これを feedback_score 的に保存し、
  - テンプレ改善の判断材料にする。

**7-3. A/B テスト（余裕が出てから）**

- 同じ用途のプロンプトを2種類用意
- 一部ユーザーをランダムで振り分け
- 滞在時間 / クリック率 / 保存率 / 課金転換 などで比較

最初からガチA/Bはやらんでいい。
v1 では「フィードバック収集の仕掛けだけ」入れておけば十分。

⸻

**8. コスト管理とレート制限**

**8-1. コストを見える化**

- 日次・月次で以下を集計：
  - 総リクエスト数
  - input / output トークンの合計
  - モデル別コスト

最低限、「コンテンツ種別ごとのコスト」「ユーザー1人あたり平均コスト」は出せるようにする。

**8-2. レート制限・制御**

- ユーザーごと / エンドポイントごとに回数制限を定義：

例：

- インタラクティブ生成：
  - 無料：1日 10回
  - 有料：制限なし or 大きめ
- バッチ生成：
  - ユーザー単位ではなく「スケジューラ側で制御」

⸻

**9. 障害・タイムアウト時の挙動**

**9-1. LLMエラー / タイムアウト**

- リトライ（最大2回程度）
- それでもダメなら：
  - ユーザーには「失敗しました」ではなく
**「今日は調子が悪いので、あとで再試行させてください」** レベルの文言
  - 例外スタックトレースをそのままユーザーに見せるのは論外。

**9-2. 部分失敗**

- バッチ生成の途中で一部ユーザーだけ失敗した場合：
  - 失敗ユーザーのリストをログに出す
  - 次回バッチで再試行 or 手動リトライ

⸻

**10. No Mercy ルール（生成・配信編）**

- 「とりあえず出せました」で満足するな。
→ **保存・配信・フィードバック・改善まで含めて"1機能"** だと思え。
- 生成結果をその場で捨てるな：
→ ログだけは最低限残せ。
データなしで改善は不可能。
- 通知・メールで全部説明しようとするな：
→ 要約＋「アプリで見る」の導線が基本。
- 無限再生成ボタンは禁止：
→ 無限に叩かれたらコスト爆死する。回数制限 or モデル切り替えを入れろ。
- 「何でもLLM」でやろうとするな：
→ 単純な整形やフィルタはコードでやれ。
LLMは「人間の頭を代替すべきところ」にだけ使う。

⸻

## ✅ 連携設計（改訂案 v10）

**0. このセクションの役割**

ゴール：
**「このプロダクトが、どの外部サービス／自前サービスと、どんなデータを・どういう方向にやり取りするか」**
を一枚で説明できるようにする。
- ここで決めるのは：
- 連携対象のリスト（LLM / Stripe / R2 / OAuth / Push / Analytics など）
- データフロー（誰が"正"か、どっち向きに同期するか）
- 認証・セキュリティ
- エラー時の振る舞い・リトライ
- ベンダーロックを避ける差し替え方針

⸻

**1. 連携対象の棚卸し**

まず、「何と連携するのか」をカテゴリごとに整理する。

```
| ID   | カテゴリ       | サービス例              | 用途                          | 方向       | 同期/非同期 |
|------|----------------|-------------------------|-------------------------------|------------|------------|
| INT1 | LLM/AI         | OpenAI                  | 添削・生成・要約             | App → 外部 | 同期       |
| INT2 | 決済/サブスク  | Stripe / StoreKit 等    | 課金・プラン管理             | 双方向     | 同期+非同期|
| INT3 | ストレージ/CDN | Cloudflare R2 / S3 等   | 画像・音声・PDF保存           | App → 外部 | 非同期多め |
| INT4 | 認証/OAuth     | Apple/Google/LINE 等    | SNSログイン                  | 双方向     | 同期       |
| INT5 | 通知           | APNs / FCM / OneSignal  | プッシュ通知                  | App → 外部 | 非同期     |
| INT6 | アナリティクス | GA4 / 自前イベントAPI   | 行動ログ・計測               | App → 外部 | 非同期     |
| INT7 | 自前サービス   | 他の自作API（かぶ見ちゃん等）| クロス連携               | 双方向     | 同期       |
```

※ プロダクトごとに実際のサービス名で埋めろ。
※ 「今は使ってないが候補」も書いとくと、後で変な横入りを防げる。
※ INT1のモデル選定・トークン予算の詳細は「コンテンツ生成・配信パイプライン設計 3-2」を参照（このセクションでは重複記載しない）。

⸻

**2. 連携方式（Pull / Push / Webhook）の方針**

**2-1. 基本ルール**

- **Pull（こちらから取りに行く）**
- 決済状態の定期確認など
- **Push（こちらから送る）**
- 通知、ログ、ストレージ保存など
- **Webhook（外部から叩かれる）**
- Stripeのイベント、外部サービス起点の更新

ここで「どの連携がどの方式か」を決める：

例）
- LLM → 同期のAPI呼び出し（Pull）
- Stripe →
- 課金開始：こちらからセッション作成（Push）
- 支払い結果：Webhookで受信
- R2 → ファイルアップロード（Push）
- GA4 → イベント送信（Push）

⸻

**3. 連携別フローデザイン（ざっくり）**

**3-1. LLM連携（例：OpenAI）**

```
[Client] → [自前API /llm/...] → [OpenAI API] → [自前API] → [DB保存] → [レスポンス]
```

- クライアント → OpenAI 直叩きは禁止（キー漏洩）
- 自前サーバ側に LlmClient 的なラッパを1個だけ用意
- ログ・トークン数・モデル名はここで記録

**3-2. 決済連携（Stripeなど）**

```
[Client] → [自前API /billing/checkout] → [Stripe Checkout] → [ユーザー完了]
         → [Stripe Webhook → /billing/webhook] → [DB: subscriptions 更新] → [アプリ側反映]
```

- 購入開始は **自前API発** に統一
- 結果確定は **Webhook** を「真実」とする（Web画面の戻りは参考程度）

**3-3. ストレージ/CDN連携**

- 原則：
- メタ情報はDB
- 実体（画像・音声）はR2/S3

フロー例：

```
[Client] → [自前API /uploads/sign-url] → [署名付きURL] ← App
[Client] → [R2/S3 に直接 PUT]   （大きいファイル）
[Client] → [自前APIにメタ情報POST] → [DB: path保存]
```

小さいファイルなら自前API経由でもいいが、将来重くなるなら最初から署名URL方式にしとけ。

⸻

**4. 認証・セキュリティポリシー（連携用）**

**4-1. 秘密情報の扱い**

- APIキー・シークレット：
- .env / Render の環境変数で管理
- Gitに絶対含めない
- アプリ内（iOS/Android/フロント）に **直書き禁止**
- どうしても必要なものは **パブリックキー or 匿名キー限定**

**4-2. Webhookの検証**

- 受信エンドポイント例：/api/v1/billing/webhook
- 必須ルール：
- 署名ヘッダ（Stripe-Signature等）検証
- IP制限できるならIP allowlist
- 冪等性（event_idで一度処理したイベントは二度処理しない）

**4-3. OAuthログイン（使う場合）**

- フローは標準3ステップ：

```
[App] → [プロバイダ認可画面] → [コード受領] → [自前API /auth/oauth/callback] → [自社JWT発行]
```

- 外部プロバイダのアクセストークンは **最低限のscope** にする
- 必要以上にユーザーデータを取りに行かない（保持しすぎると責任だけ増える）

⸻

**5. エラー・障害時の扱い（連携ごと）**

**5-1. LLMダウン or タイムアウト**

- リトライ（短時間2〜3回）
- それでも無理なら：
- ユーザーには
「今は生成に失敗しました。しばらくしてから再実行してください。」
レベルで返す
- ログにはエラー詳細＋対象ユーザーを残す

**5-2. 決済Webhook取り逃し**

- Webhookは外部側がリトライしてくれる前提だが
それでも失敗したら：
- 手動照合用に billing_events を残しておく
- 管理画面 or 管理コマンドで再同期できるようにしておく

**5-3. ストレージ障害**

- アップロード失敗時：
- DBには登録しない（ゴミレコード防止）
- すでに登録済みファイルが落ちてたら：
- UI側で「ファイルを読み込めません」＋再アップロード導線

⸻

**6. サンドボックス／本番の切り替え**

- 決済や外部APIは必ず **sandbox/staging環境** を使う。
- 設定方針：

```
- 環境ごとに .env や Render の環境変数を分ける
  - STRIPE_KEY_TEST / STRIPE_KEY_LIVE
  - OPENAI_API_KEY (本番と開発で別キー) など
```

- コード側は「環境ごとにキーを切り替えるロジック」を1か所に集約

「手元ではテストキー、本番では本番キー」に自動で切り替わるようにして、
人間の手動切り替えに頼らない。

⸻

**7. 差し替え前提の抽象化（ベンダーロック対策）**

LLM・決済・ストレージは ベンダー変える可能性が高い。
最初から「直接ライブラリ叩かない」構造にしとけ。

**7-1. 抽象クライアント例**

- LlmClient
- generate_correction()
- generate_summary() など
- PaymentGateway
- create_checkout_session()
- cancel_subscription() など
- StorageClient
- put_object()
- get_signed_url()

アプリ本体はこの「薄いインターフェース」だけ知っていればいい。
ベンダー変更は、この中身だけ差し替える。

⸻

**8. ログ・監査・コスト可視化**

**8-1. ログ**

- すべての連携について、最低限以下をログに残す：
- 呼び出し先（OpenAI / Stripe / R2 等）
- user_id（可能なら）
- 成功 / 失敗
- 所要時間
- コスト情報（LLMのトークン数など）

**8-2. コスト**

- 月次で次を集計できるようにする：
- LLM利用料（コンテンツ種別ごと）
- Stripe手数料
- ストレージ容量・転送料のざっくり額

「なんとなく使ってたら赤字になってました」はただの甘え。
コストは"設計時点"から見える化前提で組め。

⸻

**9. 自前サービス間連携（エコシステム用）**

お前は LimeStudent / こえあつめ / TripCraft / かぶ見ちゃん… と
複数アプリを将来的に「つなぐ」気満々だから、ここも書いておけ。
- ユーザー軸：
- 共通アカウントにするのか、アプリごとに分けるのか
- データ連携：
- 例：
- LimeStudentの英語記録 → こえあつめのストーリー生成に流用
- TripCraftの旅ログ → 別アプリで見返す
- 「どっちがデータのオリジナルか（System of Record）」を決める

将来グチャグチャに繋ぎ始めると死ぬから、
**「このアプリでは"参照だけ"」「ここが主に"書き込み場所"」** を先に宣言しておく。

⸻

**10. No Mercy ルール（連携設計 編）**

- フロントから外部APIを **直叩きするな**
→ すべて自前サーバ経由。キー漏洩と制御不能を避ける。
- 「とりあえずWebhook作っとくか」は禁止
→ 受けたイベントを **どうDBに反映するか** まで決めてから作れ。
- 1機能 = 1プロバイダ前提で設計するな
→ 抽象レイヤーを1枚噛ませろ。将来的に乗り換える気でいろ。
- サンドボックスと本番を **人力切替** にするな
→ 環境変数と設定で自動切替。手作業は事故る。
- 「連携が死んだら全部巻き込まれて死ぬ」構造はNG
→ LLMが死んでも履歴閲覧はできる、Stripeが死んでも既存ユーザーは利用できる、
ぐらいの"分離"は意識しろ。

⸻

## ✅ 運用・監視設計（改訂案 v10）

**0. このセクションの役割**

ゴール：
**「本番稼働後、このプロダクトをどう回し続けるか」** を決めること。
- 対象：
- 環境構成（local / staging / production）
- デプロイフロー
- ログ設計
- メトリクス & モニタリング
- アラート & 障害対応
- バックアップ & リストア
- 定期メンテ / リリース運用

ここを「そのうち考える」で放置すると、
**"直しても直しても同じところで燃えるアプリ"** が出来上がる。

⸻

**1. 環境構成**

**1-1. 環境の種類**

```
- local（開発環境）
  - 開発用Docker or ローカル環境

- staging（任意）
  - 本番とほぼ同じ構成
  - 小規模リリースの検証

- production（本番）
  - 実ユーザーが利用
```

お前の規模なら最初は local + production の2つでOK。
staging は「本番ユーザーが増えたタイミングで追加」でもいい。

**1-2. 環境ごとの差分**

- 環境変数（APIキー / DB / LLMキー / Stripeキー）
- ログレベル（localはDEBUG, 本番はINFO以上）
- ダミーメール・ダミー決済（staging only）

⸻

**2. デプロイ戦略**

**2-1. ブランチ運用**

```
- main：本番反映用
- dev：開発統合用
- feature/◯◯：機能ごとに切る
```

- 本番デプロイ = main にマージされたものだけ

**2-2. デプロイ手順（Render想定の例）**

```
1. dev ブランチで動作確認
2. main に PR / マージ
3. Render が自動デプロイ
4. ヘルスチェック（/healthz 等）で一次確認
5. 手動で主要画面を触って目視確認
```

- ロールバック方針：
- 前のバージョンのコミットに戻して再デプロイ
- DBマイグレーションが絡む場合は手順を必ずここに追記

⸻

**3. ログ設計**

**3-1. ログ種別**

- アプリケーションログ
- リクエスト開始/終了、重要なビジネスイベント
- エラーログ
- 例外スタックトレース、LLM呼び出し失敗、外部API失敗
- アクセスログ
- HTTPメソッド、パス、ステータスコード、処理時間
- LLM利用ログ
- モデル名、トークン数、処理時間、ユーザーID（可能なら）

**3-2. ログの形式・ルール**

- 形式：JSON 形式 or プレーンテキスト（どちらかに統一）
- 1リクエスト＝1 request_id を付与
- アプリログ / エラーログ / LLMログを request_id で紐づけ

```
[time] [level] [request_id] [user_id] [path] [message] [meta...]
```

**3-3. 出力先**

- local：コンソール
- production：
- Renderのログ + 必要なら外部（Sentry相当）
- 重大エラーは別途通知（メール or Discord等）

⸻

**4. メトリクス & モニタリング**

**4-1. 技術メトリクス**

最低限、これだけは意識する：

- レイテンシ：
- メインAPIの平均・P95応答時間
- エラーレート：
- 5xx, 4xx（特に429/401/403）割合
- スループット：
- 1分あたり/1時間あたりリクエスト数
- リソース：
- CPU・メモリ使用率（Renderのダッシュボードで）

**4-2. ビジネスメトリクス（KPI寄り）**

- 日次アクティブユーザー（DAU）
- LLM呼び出し回数 / ユーザー / 日
- 1ユーザーあたりの平均トークン消費量
- 課金コンバージョン（無料→有料）

ここは「完璧なダッシュボード」より、
**月1で数字を見返せる最低限** を作るのが先。

⸻

**5. 監視とアラート設計**

**5-1. 監視対象**

- HTTPヘルスチェック（/healthz）
- 5xx エラーレート（一定時間内の件数）
- レイテンシ（一定閾値を超えたか）
- LLMエラー（率 or 回数）
- バックグラウンドジョブ（バッチの失敗）

**5-2. アラートレベル**

3段階くらいで分ける：

- **INFO**：
- バッチ成功 / 定期処理完了
- 通知不要。ログだけ。
- **WARN**：
- 5xx が一時的に増えた
- LLMが数回失敗
- Slack/Discord通知レベル
- **ERROR**：
- サービス全体が落ちている
- DB接続不可
- 即時通知（メール / Discord / Push 等）

個人開発なんだから、
**「絶対起きてなきゃいけない24/7監視」まではやらなくていい。**
その代わり「明らかにヤバい時にだけ飛んでくる」くらいに絞れ。

⸻

**6. 障害対応フロー**

**6-1. 一次対応の流れ**

テンプレとして決めておく：

```
1. 検知：
   - アラート or ユーザーからの報告

2. 切り分け：
   - 自分でアクセスして再現するか確認
   - 直近デプロイの有無を確認
   - ログを見て 5xx / エラー内容を確認

3. 暫定対応：
   - 明らかにデプロイが原因なら、直前バージョンにロールバック
   - LLM関連なら一部機能を一時停止 or モデル切替

4. 恒久対応：
   - 原因分析
   - コード修正
   - テスト
   - 再デプロイ

5. 振り返りメモ：
   - 障害の概要
   - 発生日・影響範囲
   - 原因
   - 再発防止策
```

ポイントは「毎回アドリブで対応しない」こと。
テンプレあれば、寝ぼけてても最低限は動ける。

⸻

**7. バックアップ & リストア**

**7-1. バックアップ方針**

- DB（PostgreSQL）：
- Renderの自動スナップショット or 手動バックアップ
- 頻度：1日1回
- 保持期間：30〜90日目安
- ストレージ（R2等）：
- 原則削除しない（ユーザー削除要求がある場合だけ例外）
- 必要に応じてバージョニングをON

**7-2. 復旧方針（ざっくりでいいから書く）**

```
- DB破損 or 誤削除発生時：
  1. 対象サービスを一時停止（書き込み制限）
  2. 直近スナップショットから別インスタンスに復元
  3. 確認後、本番DBを切り替え
```

「バックアップはあるけどリストア方法を誰も知らない」
これが一番ダサいパターン。
手順の骨だけでもここに書いとけ。

⸻

**8. 定期メンテナンス**

**8-1. 実施内容**

- ログローテーション・古いログ削除
- 不要な generated_contents / notifications の整理
- ライブラリアップデート確認（依存パッケージ）
- セキュリティ更新（OS / ランタイム）

**8-2. 頻度**

- 月1回をベースにする（個人開発ならこれで十分）

⸻

**9. リリース運用（バージョニング）**

**9-1. アプリのバージョン付け**

- ルール例：
- MAJOR.MINOR.PATCH
- 例：1.0.0, 1.1.0, 1.1.1
- タグ運用：
- Gitタグを v1.0.0 のように付ける

**9-2. リリースノート**

- 変更点を最低限メモ：
- 新機能
- 修正
- 既知の問題

将来、自分のログ見返した時に
**「いつ何を変えたか」分からないのは普通にストレスだぞ。**

⸻

**10. セキュリティ運用**

- 秘密情報：
- すべて環境変数管理
- 定期的に漏れ・公開リポジトリをチェック
- アカウント管理：
- 管理者アカウントの2FA（可能なら）
- 依存パッケージ：
- 脆弱性情報（Dependabot 等）を定期確認

⸻

**11. No Mercy ルール（運用・監視編）**

- 「動いてるからOK」はただの現実逃避。
→ **「どれくらいの頻度で・どれくらい壊れてるか」** を数値で見ろ。
- 障害を **"なかったこと"** にするな：
→ 小さい障害でも、原因と対策を1行メモでいいから残せ。
- ログを「吐きっぱなし」にするな：
→ 見ないログ = ないのと同じ。
自分が**月1で覗く気になる粒度**にしろ。
- 個人開発だからこそ：
→ 「俺しかいない」前提で、**未来の自分を助ける設計**をしろ。
今のノリで作った"スパゲッティ運用"は数ヶ月後の自分が殺される。
